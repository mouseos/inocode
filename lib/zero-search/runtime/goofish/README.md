# Goofish signing runtime

Goofish (闲鱼) MTOP requests must be signed by Alibaba's
SecurityGuard native library — the signature comes out of
`doCommandNative(10401, …)` inside `libsgmainso-*.so`, and there
is no reimplementation of that native code, by design of the SDK.

ZeroSearch therefore runs the app's own library. A small Rust
harness (`sgharness`, sources in `crates/helpers/goofish-signer`)
loads the genuine library under the Unicorn CPU emulator
(AArch64), initialises the SDK the way the app does, answers the
JNI calls the library makes, and serves signatures over stdio in
a JSON-lines "serve" protocol:

```jsonc
// server -> harness
{"input": "<mtop INPUT string>", "requestType": 7, "authCode": ""}
// harness -> server (one per line)
{"sign": "<52 hex chars>"}
// harness, once, at startup
{"ready": true, "initRc": 0, "appKey": "21407387"}
```

(`appKey` may be included in a request; the harness uses its own
initialised appKey either way.) Through v0.4.0 the same protocol
was served by a JVM + unidbg harness; the Rust harness replaced
it after it was verified to produce byte-identical signatures for
the fixed test input (the golden vector both harnesses share) and
to have a live search accepted by Goofish's servers. The JVM
sources are kept under `harness/` as a development reference.

## How a release install works (zero configuration)

The release packages ship a **payload** next to the server binary
(~7 MB in total, measured on Linux x64 — the v0.4.0 JVM payload
was ~145 MB expanded):

```
<install dir>/
  zero-search-mcp[.exe]
  goofish-payload/
    signer/
      sgharness[.exe]     # the Rust signing harness
    syslibs/              # Android SDK 23 system libraries the
                          # harness loads SecurityGuard against
    payload.json          # payload manifest (format 2) + the
                          # app-package source
```

The one component that cannot be shipped is the Goofish app
package itself (~269 MB, Alibaba-proprietary). On the first
Goofish use — normally in the server's background pre-warm, before
any MTOP request exists — the server assembles the runtime in its
own data directory (`~/.local/share/zero-search-mcp/goofish-runtime/`
on Linux, the platform equivalent elsewhere):

1. download the pinned app package (idlefish **7.28.70**, the
   build the harness emulates) from Tencent's app-store CDN —
   the URL is content-addressed by the package's MD5 and recorded
   in `payload.json` — and verify its SHA-256 and size;
2. extract the SecurityGuard `.so` libraries from the package;
3. stage the emulator rootfs: the directory skeleton, plus the
   package hard-linked (copied where hard links are unavailable)
   to `rootfs/data/app/com.taobao.idlefish-1/base.apk` —
   SecurityGuard opens its own package from that path to read its
   signing certificate, and without it initialisation "succeeds"
   but every signature is wrong;
4. generate `serve.sh` / `serve.cmd`, which execs the payload's
   signer binary with the runtime's rootfs, the extracted main
   library and the payload's `syslibs/` directory.

The marker (`provision.json`, format 2) records the signer kind
alongside the payload format, platform, package version + SHA-256
and main library name. A runtime assembled by the older JVM
provisioning has a different marker and is re-assembled in place
on first use — the downloaded package is kept and reused; only
the staged files are rebuilt.

The device identity is generated by the server itself (the app's
own UTDID algorithm) and persisted next to the runtime. Nothing
is configured by the user: no JDK, no Maven, no APK hunt, no
environment variables. The harness starts once per server
process and is reused for calls whose signing context matches;
the emulator worker latches to one request identity, so the
provider restarts the harness when the signing context changes
or the verified latch envelope is exceeded, and if the harness
process dies the signer restarts it (bounded). The server's
process-group / PDEATHSIG handling still guarantees no orphan
harness outlives the server.

Harness boot takes ≈90 s under Unicorn on a loaded machine (the
JVM boot took 135–280 s); the provider's startup budget is
unchanged at 900 s, which also covers the first-call download.

Disk budget: ~7 MB for the installed payload; in the data
directory, the app package (269 MB), the extracted libraries
(~5 MB) and small working files — the staged rootfs copy of the
package is a hard link, so budget a second 269 MB only on
filesystems without hard-link support.

## Building the payload (release time only)

```sh
./build-payload.sh linux-x64     # or win32-x64 / macos-arm64
# → runtime/goofish/payload-dist/<platform>/goofish-payload
```

`build-payload.sh` packs the signer binary (`$GOOFISH_SIGNER_BIN`
if set, else the conventional build output of
`crates/helpers/goofish-signer`, else it builds that crate with
cargo), extracts the six Android system libraries from the
pinned `unidbg-android` 0.9.9 jar (downloaded from Maven Central,
SHA-256-verified; only the `android/sdk23/lib64` entries are
used — `libcpp.so` ships under the name the loader looks for,
`libc++.so` — and nothing of unidbg itself ships), and writes
`payload.json` (format 2) from pinned constants that must match
the provider's provisioning defaults
(`crates/providers/goofish/src/provision.rs`). No JDK and no
Maven are involved anymore. The release workflow runs it for
every platform and packs the result into both the installer ZIP
and the .mcpb. `scripts/pack-mcpb.sh` picks the same directory up
for local packing.

The signer crate lives outside the workspace on purpose: its
Unicorn build drives cmake and bindgen and needs libclang, and
must never be able to break the main workspace build — the same
isolation pattern as the Yahoo US image helper. Unicorn is built
for AArch64 only, the one architecture the harness emulates.

## Legacy paths: `bootstrap.sh` and the JVM harness

`bootstrap.sh` is the older, manual assembly route: given an APK
you supply, a JDK 8 and Maven, it builds a self-contained
`goofish-runtime/` bundle around the JVM harness. It is kept for
development; release installs do not use it, and the server
re-assembles bootstrap/JVM-era runtimes into the Rust form on
first use (see the marker note above). `verify-bundle.sh` below
applies to bootstrap-assembled bundles only.

## Layout of an assembled runtime

```
goofish-runtime/          (in the server's data directory)
  serve.sh / serve.cmd    # entry point the server spawns
  goofish.apk             # the downloaded app package
  libs/                   # SecurityGuard .so files from the package
  rootfs/                 # emulator root filesystem, staged by
                          #   provisioning (incl. the base.apk link)
  state/                  # SDK working files + request latch
  logs/                   # harness stderr
  provision.json          # provisioning marker (format 2)
```

## Verifying a bootstrap-assembled bundle

For bundles assembled by `bootstrap.sh` (the legacy JVM path):

```sh
./verify-bundle.sh /path/to/goofish-runtime
```

The checks are static (the harness is not started): `serve.sh`
exists and is executable; `goofish.apk` is a readable zip carrying
the arm64 SecurityGuard libraries; the compiled `SgHarness` class
and the patched classes exist; every jar on `serve.sh`'s classpath
exists under `m2repo/`; `libs/` holds the extracted SecurityGuard
`.so` set; `rootfs/` exists; and a JDK 8 is resolvable the same way
`serve.sh` resolves it. Each check prints `[OK]` or `[FAIL]` with
the offending item named, and the script exits non-zero on any
failure. Server-assembled (Rust) runtimes are instead verified by
the golden-vector gate before any live use: the fixed synthetic
INPUT shared by both harnesses must sign to the recorded value —
a mismatch means the emulation drifted and live calls must not
proceed.
