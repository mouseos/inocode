# リポジトリを広く把握する技術：研究の調査

- **対象と範囲：** エージェントがリポジトリ全体をつかむ技術。どこに何があるか、モジュールの関係、どこを変えるべきかを扱う。ユーザーの方針は「機械的処理でできるところはそれでいい。とにかくトークン食わずに正確性を上げたい」（2026-11-17）。
- **関連コード：** `core/src/outline.rs`（`outline`）。関係する既存のツールは `read`（100 行の窓）と `shell`。
- **根拠の状態：** `outline` と名前検索は RESEARCH_SUPPORTED（Agentless、LocAgent。どちらも Python の研究）。2026-11-17 に承認。
- 略記：「査読あり」「査読前」。数値は各論文の表から取った。

| 参照の多さで順位を付けた地図（Aider 式） | 査読前 | 8k トークン内の有用な情報が最多（0.379）。Recall@20 0.633（埋め込みは 0.703、BM25 は 0.445）。Qin, Xie, arXiv 2607.24882 | 索引が要る | ファイル単位のみ。修正の成否は測っていない |

根拠が見つからなかったもの：
- ファイル一覧や地図を文脈に入れるかどうかの対照研究
- 並列やサブエージェントでの探索
- LSP の査読ありの研究
- Rust のリポジトリでの研究（ほぼすべて Python）

強いモデルほど効果が小さい：Bellam（査読前）が直接測った。KGCompass（査読前）でも同じ傾向。

## 提案（承認済み）

トークン 1 つあたりの正確さが高く、LLM を呼ばずに作れるものに絞る。

1. `outline`：ファイルやフォルダの骨格を返す。関数・型・メソッドのシグネチャと位置だけを返し、本体は返さない。構文木で機械的に作る（Agentless の骨格）。
2. `find`：中身の検索（ベンチマーク中）に、名前の検索（関数名・型名から定義の場所）を加える。結果はまとめて件数に上限を付ける（LocAgent の名前検索、SWE-agent の検索）。
3. 入れない：
   - LLM による要約
   - 埋め込み
   - 2 段以上のグラフ
   - LSP
4. 見送る：1 段のコードグラフ（呼び出し元・呼び出し先）。効果は 2 ポイント前後で、大きなモデルでは有意でない。

## 言語によらない方法（2026-11-17 の追加調査）

| 技術 | 査読 | 結果 | 限界 |
|---|---|---|---|
| 骨格による絞り込みは Python 以外で大きく落ちる | 査読前 | ファイル単位の再現率。Agentless（骨格）：Python 60.9%、Java 29.5%、JS 23.4%、TS 17.5%。Aider（地図）：58.2%、41.7%、37.1%、33.3%。SWE-PolyBench, Rashid et al., arXiv 2504.08703 | Claude 3.5 Sonnet のみ。骨格だけを外す実験ではない |
| Python 以外の言語では、どの方式も場所の特定に失敗することが多い。リポジトリ全体のファイル一覧は、大きな TS のリポジトリで文脈からあふれた | 査読前 | 最高の解決率：Java 23.44、Rust 15.90、C++ 14.73、TS 11.61、C 8.59、Go 7.48、JS 5.06。Multi-SWE-bench, Zan et al., arXiv 2504.02605 | 技術ごとの分解実験はない |
| 他のファイルから BM25 で集めた文脈は、言語を問わず効く | 査読あり | 完全一致の改善：Python +6.90、Java +7.52、C# +9.10、TS +1.96。密な検索との差は 0.1〜1.8。CrossCodeEval, Ding et al., NeurIPS 2023 | 補完の課題で、場所の特定ではない |
| 文書：見出しの目次とセクションを読むツール | 査読前 | 正答率 79.5%（比較の方式は 69.2%）。ただし、正答 1 件あたりのトークンは 6,770（比較の方式は 4,978）と増えた。DeepRead, arXiv 2602.05014 | 目次を外す実験はない。作業途中の報告 |
| 文書：LLM で要約の木を作る | 査読あり | QuALITY 82.6%。ただし木をたどるより、全ノードを平らに検索するほうが良かった。RAPTOR, ICLR 2024 | 作るのに LLM が要る。要約の約 4% に軽い幻覚 |
| 文書：ページごとの要点を作る | 査読あり | QuALITY 86.16%（全文は 85.83%、BM25 は 84.42%）。単語は 13.8〜25.4% 少ない。ReadAgent, ICML 2024 | 作るのに LLM が要る |
| ログ：grep と末尾を組み合わせる | 査読前 | 品質は grep 単独と同程度で、トークンは 4.5 分の 1。LogDx-CI, arXiv 2605.28876 | 35 件、著者 1 人 |

- 根拠が見つからなかったもの：
  - 字下げによる折りたたみ
  - 正規表現や ctags による骨格
  - n-gram による骨格
  - 設定ファイルの読み方
  - 「目次を先に見せる」ことだけを取り出した対照実験
- 言語によらず最も根拠があるのは、キーワード検索で結果をまとめて件数に上限を付けることと、窓を区切って読むこと。この 2 つは `find` と `read` にあたる。
- `outline` への影響：骨格の効果は Python 以外では弱い可能性がある（SWE-PolyBench、査読前）。

## outline の実装（工学上の選択で研究なし）

- 構文木：tree-sitter 0.27 と tree-sitter-tags。各言語の部品に同梱された tags.scm で、定義の場所と名前を取る。
  - 対応する言語：Rust・Python・JavaScript・TypeScript・TSX・Go・Java・C・C++。
  - TypeScript は、JavaScript と TypeScript の tags.scm を合わせて使う。
- 表示：定義が始まる行を、字下げ（入れ子が分かる）と行番号つきでそのまま出す。本体は出さない。Agentless の骨格に近いが、フィールドやコメントは出さない。
- フォルダを指定した場合：`.gitignore` に従ってファイルを集め、対応する言語のファイルだけを並べる。
- 上限：1 回 300 行。2MB を超えるファイルは、生成されたコードとみなして飛ばす。
- tree-sitter の 8 言語以外：ハイライト用の文法（syntect と two-face、約 220 文法）の印 `entity.name.<種類>` から定義を取る（2026-11-17 にユーザーが「併用」を承認。下の比較を参照）。
  - 種類：function・class・type・struct・enum・trait・interface・namespace・impl・module・section。section は文書の見出し。
  - 呼び出しや型の参照（`meta.function-call` など）、文書の中のコード（`markup.raw`）にある印は除く。
  - 定義の印を一つも持たない文法（JSON・YAML・平文など）は、解析せずに飛ばす。
- 言語の追加：データベースの横の `<データベース名>.files/grammars/` に `.sublime-syntax` を置けば、再ビルドせずに読む。読むのはプロセスごとに 1 回。
- テスト：`outline.rs` の単体テスト。
  - Rust・Python・TypeScript の定義と字下げ。
  - フォルダで対応外のファイルを飛ばすこと。
  - 全言語の設定が読めること。
  - Ruby の定義と Markdown の見出し（コードブロックの中は除く）。JSON は対象外になること。

## ハイライト用の文法と tree-sitter の比較（プロジェクト内の実測、2026-11-17）

- 発端（ユーザーの提案）：ハイライト用の文法の印（`entity.name.function` など）から定義を取れば、多くの言語に対応でき、言語を後から足せるのではないか。
- 比べたもの：
  - syntect 5.3.0（Sublime Text 形式の文法、Oniguruma）。文法のセットは syntect の標準と、two-face 0.5.2（bat の文法）の 2 通り。
  - tree-sitter 0.27.2 の tags。
  - tree-sitter の結果を基準にし、（名前, 行）で照合した。食い違いは標本を目で確かめた。
- 手順とコード：`refs/outline-bench`（git 管理外）。

| 対象 | 標準セット | two-face |
|---|---|---|
| Rust（codex、2,302 ファイル） | P .920、R .995 | P .920、R .999 |
| TypeScript（deepseek-harness、515 ファイル） | 文法なし | 生の結果 P .073。手で絞り込んで P .739、R .995 |
| Python（346 ファイル） | P 1.000、R .800 | P 1.000、R .800 |
| Go（376 ファイル） | P .998、R .997 | P .979、R .998 |
| C（280 ファイル） | P .968、R .972 | P .979、R .971 |

- 食い違いの中身：
  - Rust：syntect だけが拾ったものの多くは `impl` ブロックとトレイトのシグネチャで、有用。クロージャは誤り。
  - Python：取りこぼしは、すべてモジュール直下の定数（tree-sitter の `constant`）。これを除くと再現率は 100%。
  - TypeScript：関数呼び出しや型の参照まで定義として印が付く。手で絞り込みの規則を作っても、適合率は .739 にとどまる。
- 速さ（1 秒あたりの行数）：tree-sitter は 151k〜351k、syntect は 12.9k〜78k で、3〜12 倍遅い。
  - フォルダ全体：codex-rs/tui（1,246 ファイル）で tree-sitter は 1.05 秒、syntect は 4.0〜4.4 秒。
- 対応言語：
  - 定義の印を持つのは、標準セットで 75 中 40、two-face で 220 中 103。
  - Swift・Nim・Nix・Vue・Svelte は、どちらにも印がない。
  - Markdown の `#` 見出しは `entity.name.section.markdown` として取れる。
- 実行中の追加：`.sublime-syntax` をフォルダに置けば、再ビルドせずに読める（`yaml-load` 機能。読み込みに 104ms）。
- 費用：
  - バイナリへの追加：tree-sitter の 8 言語は +11.29MB、syntect の標準セットは +1.06MB、two-face は +1.68MB。
  - ビルドの時間：tree-sitter 30.6 秒、syntect 21.6〜23.8 秒。
- ライセンス：
  - two-face の文法は MIT・Apache-2.0・BSD。
  - syntect の標準セットの文法のライセンスは確認していない。
- 限界：
  - 各数値は 1 回だけの計測。
  - 何を定義とみなすか（`impl`、クロージャ、マクロ、定数）は、計測した人の判断。
