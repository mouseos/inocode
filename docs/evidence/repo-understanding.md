# リポジトリを広く把握する技術：研究の調査

- **対象と範囲：** エージェントがリポジトリ全体をつかむ技術。どこに何があるか、モジュールの関係、どこを変えるべきかを扱う。ユーザーの方針は「機械的処理でできるところはそれでいい。とにかくトークン食わずに正確性を上げたい」（2026-11-17）。
- **関連コード：** `core/src/outline.rs`（`outline`）。関係する既存のツールは `read`（100 行の窓）と `shell`。
- **根拠の状態：**
  - `outline` と名前検索は RESEARCH_SUPPORTED（Agentless、LocAgent。どちらも Python の研究）。2026-11-17 に承認。
  - ただし `outline` の根拠は限定的で、設定が inocode と一致しない（下の「outline の根拠の再確認」）。
  - inocode 上の実測では、`outline` の有無で正確さにもトークンにも差は見られなかった（下の「outline の効果の実測」）。
- 略記：「査読あり」「査読前」。数値は各論文の表から取った。

根拠が見つからなかったもの：
- ファイル一覧や地図を文脈に入れるかどうかの対照研究
- 並列やサブエージェントでの探索
- LSP の査読ありの研究
- Rust のリポジトリでの研究（ほぼすべて Python）

強いモデルほど効果が小さい：Bellam（査読前）が直接測った。KGCompass（査読前）でも同じ傾向。

## 提案（承認済み）

トークン 1 つあたりの正確さが高く、LLM を呼ばずに作れるものに絞る。

1. `outline`：ファイルやフォルダの骨格を返す。関数・型・メソッドのシグネチャと位置だけを返し、本体は返さない。構文木で機械的に作る（Agentless の骨格）。
2. `find`：中身の検索（ベンチマーク中）に、名前の検索（関数名・型名から定義の場所）を加える。結果はまとめて件数に上限を付ける（LocAgent の名前検索、SWE-agent の検索）。
3. 入れない：
   - LLM による要約
   - 埋め込み
   - 2 段以上のグラフ
   - LSP
4. 見送る：1 段のコードグラフ（呼び出し元・呼び出し先）。効果は 2 ポイント前後で、大きなモデルでは有意でない。

## outline の根拠の再確認（2026-11-17、原文で確認）

- 出典：Xia, Deng, Dunn, Zhang, "Agentless: Demystifying LLM-based Software Engineering Agents", FSE 2025（査読あり。会議の掲載ページ https://conf.researchr.org/details/fse-2025/fse-2025-research-papers/85 で確認）、arXiv 2407.01489v2 の Table 2・5.2.1 節。
- 確かめた数値：クラス・関数単位で、正しい場所を含む割合。
  - ファイル全体：53.67%、778 行、$0.15。
  - 骨格：58.33%、698 行、$0.02。
  - モデルは GPT-4o、課題は SWE-bench Lite。
- 原文の骨格の中身：クラスと関数の見出し、クラスのフィールド、メソッドのシグネチャ、クラスとモジュールの階層にあるコメント。
- inocode の設定との違い：
  1. Agentless では、骨格は毎回必ず実行する固定の手順。疑わしいファイルの骨格をまとめて 1 回で渡す。エージェントが呼ぶツールではない。
  2. 比べたのは「ファイル全体」とだけ。名前だけを渡す方式との比較はない。
  3. 場所の特定の精度だけを測っている。修正の成功率への効果は報告されていない。
  4. モデルは 1 つ、言語は Python だけ。各 1 回の実行で、有意差の検定はない。
  5. （2026-11-17 に対応済み）tree-sitter の 8 言語では、原文と同じくフィールドと、関数の外のコメントも出す。ハイライト用の文法で扱う言語は、定義の行だけ（関数本体の範囲が分からないため）。
  6. Python 以外では、骨格による絞り込みが大きく落ちる、という報告がある（SWE-PolyBench、査読前。下の表）。
- inocode の中で、`outline` がエージェントの正確さやトークンを改善するかは測っていない。プロジェクト内のベンチマークは、定義を取り出す正確さと速さだけを測った。

- 根拠が見つからなかったもの：
  - 字下げによる折りたたみ

## outline の実装（工学上の選択で研究なし）

- 構文木：tree-sitter 0.27 と tree-sitter-tags。各言語の部品に同梱された tags.scm で、定義の場所と名前を取る。
  - 対応する言語：Rust・Python・JavaScript・TypeScript・TSX・Go・Java・C・C++。
  - TypeScript は、JavaScript と TypeScript の tags.scm を合わせて使う。
- 表示：定義が始まる行を、字下げ（入れ子が分かる）と行番号つきでそのまま出す。本体は出さない。Agentless の骨格に近いが、フィールドやコメントは出さない。
- フォルダを指定した場合：`.gitignore` に従ってファイルを集め、対応する言語のファイルだけを並べる。
- 上限：1 回 300 行。2MB を超えるファイルは、生成されたコードとみなして飛ばす。
- tree-sitter の 8 言語以外：ハイライト用の文法（syntect と two-face、約 220 文法）の印 `entity.name.<種類>` から定義を取る（2026-11-17 にユーザーが「併用」を承認。下の比較を参照）。
  - 種類：function・class・type・struct・enum・trait・interface・namespace・impl・module・section。section は文書の見出し。
  - 呼び出しや型の参照（`meta.function-call` など）、文書の中のコード（`markup.raw`）にある印は除く。
  - 定義の印を一つも持たない文法（JSON・YAML・平文など）は、解析せずに飛ばす。
- 言語の追加：データベースの横の `<データベース名>.files/grammars/` に `.sublime-syntax` を置けば、再ビルドせずに読む。読むのはプロセスごとに 1 回。
- テスト：`outline.rs` の単体テスト。
  - Rust・Python・TypeScript の定義と字下げ。
  - フォルダで対応外のファイルを飛ばすこと。
  - 全言語の設定が読めること。
  - Ruby の定義と Markdown の見出し（コードブロックの中は除く）。JSON は対象外になること。

## ハイライト用の文法と tree-sitter の比較（プロジェクト内の実測、2026-11-17）

- 発端（ユーザーの提案）：ハイライト用の文法の印（`entity.name.function` など）から定義を取れば、多くの言語に対応でき、言語を後から足せるのではないか。
- 比べたもの：
  - syntect 5.3.0（Sublime Text 形式の文法、Oniguruma）。文法のセットは syntect の標準と、two-face 0.5.2（bat の文法）の 2 通り。
  - tree-sitter 0.27.2 の tags。
  - tree-sitter の結果を基準にし、（名前, 行）で照合した。食い違いは標本を目で確かめた。
- 手順とコード：`refs/outline-bench`（git 管理外）。

| 対象 | 標準セット | two-face |
|---|---|---|
| Rust（codex、2,302 ファイル） | P .920、R .995 | P .920、R .999 |
| TypeScript（deepseek-harness、515 ファイル） | 文法なし | 生の結果 P .073。手で絞り込んで P .739、R .995 |
| Python（346 ファイル） | P 1.000、R .800 | P 1.000、R .800 |
| Go（376 ファイル） | P .998、R .997 | P .979、R .998 |
| C（280 ファイル） | P .968、R .972 | P .979、R .971 |

- 食い違いの中身：
  - Rust：syntect だけが拾ったものの多くは `impl` ブロックとトレイトのシグネチャで、有用。クロージャは誤り。
  - Python：取りこぼしは、すべてモジュール直下の定数（tree-sitter の `constant`）。これを除くと再現率は 100%。
  - TypeScript：関数呼び出しや型の参照まで定義として印が付く。手で絞り込みの規則を作っても、適合率は .739 にとどまる。
- 速さ（1 秒あたりの行数）：tree-sitter は 151k〜351k、syntect は 12.9k〜78k で、3〜12 倍遅い。
  - フォルダ全体：codex-rs/tui（1,246 ファイル）で tree-sitter は 1.05 秒、syntect は 4.0〜4.4 秒。
- 対応言語：
  - 定義の印を持つのは、標準セットで 75 中 40、two-face で 220 中 103。
  - Swift・Nim・Nix・Vue・Svelte は、どちらにも印がない。
  - Markdown の `#` 見出しは `entity.name.section.markdown` として取れる。
- 実行中の追加：`.sublime-syntax` をフォルダに置けば、再ビルドせずに読める（`yaml-load` 機能。読み込みに 104ms）。
- 費用：
  - バイナリへの追加：tree-sitter の 8 言語は +11.29MB、syntect の標準セットは +1.06MB、two-face は +1.68MB。
  - ビルドの時間：tree-sitter 30.6 秒、syntect 21.6〜23.8 秒。
- ライセンス：
  - two-face の文法は MIT・Apache-2.0・BSD。
  - syntect の標準セットの文法のライセンスは確認していない。
- 限界：
  - 各数値は 1 回だけの計測。
  - 何を定義とみなすか（`impl`、クロージャ、マクロ、定数）は、計測した人の判断。

## outline の効果の実測（プロジェクト内の実測、2026-11-17〜18）

- 目的：`outline` があるとエージェントの正確さとトークンが良くなるかを、inocode 上で確かめる（ユーザーの依頼「根拠ないもの余り採用したくないので」）。
- 設計：
  - 課題：SWE-bench Lite から 40 件（シード 20261117。django 12、pytest 12、sphinx 8、scikit-learn 8）。正解は各件のパッチが触るファイルと関数。
  - 作業：バグの場所の特定だけ（編集もテストもしない）。最後に最大 10 件の場所を順位付きで答える。
  - A 版は `outline` あり、B 版は `outline::spec()` だけを外した別ビルド。各件を 2 回ずつ、A と B を 1 ターンずつ交互に回す（計 160 ターン）。
  - 指標：File Acc@1・@5、Function Acc@5、トークン、モデル呼び出しの回数、時間。正確さは McNemar の正確検定、量は Wilcoxon の符号順位検定（40 組）。
  - 手順とコード：`refs/outline-agent-bench`（git 管理外）。`scripts/pilot_haiku.py`、`scripts/analyze_haiku.py`、`results/summary-haiku.json`。
- モデル：Claude OAuth の `claude-haiku-5-5`（160 ターンすべて完了、再試行なし）。

| | A（outline あり） | B（なし） | 検定 |
|---|---|---|---|
| File Acc@1 | 0.9625 | 0.9625 | p = 1.0 |
| File Acc@5 | 0.975 | 0.9875 | p = 1.0 |
| Function Acc@5 | 0.95 | 0.9625 | p = 1.0 |
| 入力トークン（中央値） | 19,675 | 19,943 | p = 0.61 |
| 出力トークン（中央値） | 1,287 | 1,410 | p = 0.26 |
| 合計トークン（組ごとの差の中央値 A−B） | +821 | | p = 0.69 |
| 呼び出し回数（中央値） | 4 | 4 | p = 0.41 |
| `outline` を呼んだターン | 80 中 11 | — | |

- 結果：正確さにもトークンにも差は見られなかった。
- 不具合でないことの確認（記録の点検）：
  - A の `outline` の呼び出し 11 回は、すべて骨格を返した（エラーは 0 回）。1 件を元のソースと突き合わせ、行番号と中身が合うことを確かめた。
  - B のターンでは `outline` は一度も呼ばれず、存在しないツールを呼ぼうとした記録もない。
  - 指示：inocode のシステムプロンプトは 1 文だけで、ツールの使い方には触れない。課題文も `outline` に触れない。モデルが知る手がかりはツールの説明文（「読む前に中身を見るのに使う」）だけ。
  - 両方の版で最も多く使われたのは `find`（A 199 回、B 206 回）と `read`（A 185 回、B 184 回）。
- 途中までの別モデルの結果（参考）：DeepAI の `deepseek-v4.1-flash` で 37 ターン（A 19、B 18）を回した時点で、正確さは A 0.95〜1.00、B 0.94 で差はなく（p = 1.0）、`outline` を呼んだのは 19 中 1 ターンだった。DeepAI が接続を断り続けたため中止した。
- 限界：
  - 正確さがほぼ満点に近く、差が出る余地が小さい（天井効果）。有名なリポジトリなので、モデルが中身を覚えている可能性がある。
  - モデルが `outline` をほとんど呼ばないため、この設計で測れるのは「ツールを置いたときの効果」であり、「骨格を読んだときの効果」ではない。
  - 作業は場所の特定だけ。言語は Python だけ。モデルは小さなもの 1 つ。
  - 差が見られないことは、効果がないことの証明ではない。この標本の大きさで小さな差は検出できない。
- 根拠の状態への影響：Agentless の結果（固定の流れの中で骨格を渡すと精度が上がる）は、inocode のツールとしての `outline` には、この条件では再現しなかった。
