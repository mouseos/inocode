# 記憶をエージェントの作業につなぐ：根拠・トークン費用・使われ方

- **対象と範囲：**
  - `project-memory.md` の保存層（教訓・手順・根拠台帳・知識、プロジェクト内と共通の範囲）を、作業中のエージェントが書き・読めるようにするかの判断材料。
  - 規則（`rules-and-local-issues.md`）の登録手段も含む。
  - 実装したのは「発見の自動記録」（下の「実装：発見の自動記録と差し込み」）だけ。ほかの案は未実装。
- **関連コード：**
  - `core/src/remember.rs`：ターンの終わりの発見の取り出しと照合。
  - `core/src/turn.rs`：成功したツール結果を集め（`observed`）、ターンの終わりに `remember` を呼ぶ。`system_prompt` は「コーディングエージェントである」の 1 文と AGENTS.md の全文だけで、ツールの使い方は書いていない。
  - `core/src/agent_tools.rs`：`render_lessons` が教訓に加えて事実を 1 件差し込む。`lesson`（書く）と `recall`（検索で読む）は従来どおり。
- **根拠の状態：**
  - 発見の自動記録：UNSUPPORTED_APPROVED（2026-11-19 の承認、下記）。作業の後に記憶を取り出して確かめてから残すことは研究で支持される（ReasoningBank、MemGuard、VibeMemBench）が、ツール出力との照合で確かめる方式そのものの研究はない。
  - そのほかの設計案：UNSUPPORTED_PENDING。

- カーネルの実験 335 ターン（`refs/kernel-bench` の `runs-comp`・`runs-limit`・`runs-hard`・`runs-cd`、Haiku 5.5）のツール呼び出し：

  - これらの課題は読むだけの 1 ターンの課題で、記憶のツールが要らなかった可能性もある。

### プロジェクトをまたぐ共有

- 共有と同じプロジェクト内とを分けて比べた研究は見つからなかった。
- Wang et al., MemGovern, arXiv 2601.06789（査読前）：GitHub の人の記録から作った経験カード 135K 枚で +2.4〜9.4 ポイント（8 モデル）。**トークンと費用はすべてのモデルで増えた**（Kimi-K2 では費用が 2 倍）。加工しない記録の効果は不安定。
- CTIM-Rover：リポジトリ単位の教訓（31%）は一般の教訓（36%）より悪かった（45 問）。

### 根拠の照合（ハルシネーション対策）

- コーディングエージェントの中で、引用を出典の本文と照合する仕組みの効果を測った研究は見つからなかった。
- Magesh et al., J. Empirical Legal Studies 22(2), 2025（査読あり）：出典を取り出してから答える法律調査ツールでも、17〜33% は作り話を含んでいた（数値は二次資料）。取り出すだけでは防げない。
- Jain et al., ICSE 2025 SEIP（査読あり）：API の文書を渡すと、あまり使われない API の正しい呼び出しが 38.58% → 47.94%。**取り出しが悪いと、よく使われる API で 39.02 ポイント悪化**。必要なときだけ取り出すと +8.20。
- Kim et al., HALLMARK, arXiv 2607.18360（査読前）：規則による確認の後に LLM を使うと、検出 0.990・誤検出 0.037。LLM だけでは誤検出 0.478。
- Rao et al., arXiv 2604.03173（査読前、要旨のみ）：URL を確かめる道具を渡すと、存在しない URL が 1% 未満に減った。中身が主張を支えるかは確かめていない。
- Liu et al., "Who Checks the Citations?", arXiv 2606.21155（査読前、要旨のみ）：最良の確認役（GPT-5）でも、法律の引用の誤りの再現率 84.4%・F1 55.0%。

### トークン費用

- ツールの数：LongFuncEval（arXiv 2505.10570、査読前）で、ツールの一覧が 49 → 741 個に増えると正答が 7〜85% 下がった。RAG-MCP（arXiv 2505.03275、査読前）は、必要なツールだけ渡すとプロンプトが半分以下、選択の正答 13.62 → 43.13%。
- キャッシュ：Lumer et al., "Don't Break the Cache", arXiv 2601.06007（査読前）：キャッシュで費用 41〜80% 減。変わる内容までキャッシュに含めると、かえって遅くなることがある。システムプロンプトだけをキャッシュするのが最も安定。
- 長い会話での指示の劣化：Laban et al., ICLR 2026：複数ターンで平均 39% 低下。最後にまとめ直しても完全には戻らない。

## 調査からの読み取り（推測。研究の結論ではない）

1. **効果は小さく、条件つき。** コーディングでは、強いモデルで +1〜5 ポイント程度。手数は減るが、トークンは増えることが多い。
2. **選別しない記憶は害になる。** エージェントが自分で書いただけの記憶は、効果なしか悪化（SkillsBench、SWE-ContextBench、VibeMemBench、CTIM-Rover）。検証済みのものだけ使うと効く（VibeMemBench、MemGuard）。
   - inocode の「候補 → 有効」の設計（`project-memory.md` の判断 7）はこれに合う。
3. **出すのは 1 件に絞る。** 2 件以上で下がる（SWE-Exp）、無関係なものが誤らせる（CTIM-Rover、Jain et al.）。
4. **使わせるには、ツールを置くだけでは足りない。** プロジェクト内でも研究でもそうなっている。ハーネスが差し込む方式のほうが、根拠がある（Proactive Memory Agent。ただし査読前で差は小さい）。
5. **根拠台帳は、機械で確かめられる部分だけが確実。** URL が存在する、引用した文が取得した本文にある、という確認。中身が主張を支えるかの判定は、LLM でも誤りが多い。

- 共有の範囲：分けて比べた研究がないため、プロジェクト内を既定とし、共有は人が選んだものだけにする案。
- 効果の確かめ方：記憶が効くかは 1 回の課題では測れない。同じリポジトリで関連する課題を順に解かせ、記憶あり・なしを比べる実験が要る（SWE-ContextBench の方式）。設計は未定。

## 実装：発見の自動記録と差し込み

- 動き方：
  1. ターン中、エラーでないツール結果を集める。
  2. ターンが `completed` で終わり、スレッドにプロジェクトがあり、集めた結果が 1 件以上あるときだけ、モデルに 1 回だけ要求を送る。内容は「このターンでツール結果が示した、後の作業に役立つ事実を、示した部分の原文の引用つきで JSON の配列で挙げよ」。
     - 会話とツールの一覧はターンと同じものを送る。前の部分のキャッシュを共有するため。答えの中のツール呼び出しは無視する。
     - この要求と答えはスレッドに保存しない。
  3. 引用が 12 文字以上あり、集めたツール結果のどれかに含まれるもの（`rules_import::quotes` と同じく、書式と空白の違いは無視）だけを、プロジェクトの根拠（claim、検証済み）として保存する。
  4. 同じ題名の検証済みの根拠がすでにあれば保存しない。
  5. 以後のターンの初めに、依頼の文で検索して最も合う事実（検証済み・承認済みの根拠、または知識）を 1 件だけ、教訓と一緒に要求の末尾に付ける。
- 失敗しても（要求の失敗、JSON でない答え）ターンは失敗にしない。何も保存しないだけ。
- トークン：対象のターンごとに要求が 1 回増える。会話の部分はキャッシュに入る見込みで、主な費用は短い指示と答え。実測はしていない。
- しないこと：
  - 「だからこうする」というやり方（手順）は取り出さない。確かめる手段（テストの成否など）がまだないため。
  - プロジェクト共通の範囲には保存しない（共有の効果を分けて測った研究がない）。
  - プロジェクトのないスレッドでは動かない（保存する先がない）。
- 例（ユーザーが挙げたもの）：「このメモリ領域は再起動後も保たれる」をツール出力が示していれば、その事実が引用つきで残る。「ログはここに書く」という判断は、差し込まれた事実を見たモデルが行う。

## 実装・検証の状況

- 単体テスト（`remember.rs`）：答えから JSON の配列を読むこと。ツール出力にある引用だけが残り、作り話・短すぎる引用・空の事実は残らないこと。
- TCP テスト（`turn_tcp.rs` の `facts_quoted_from_tool_output_are_kept_and_shown_in_later_work`）：
  - ファイルを読んだターンの後に、要求が 1 回増える（計 3 回）。その要求はスレッドに保存されない。
  - 引用がツール出力にある事実だけが保存され、出力にない事実は保存されない。
  - 同じプロジェクトの新しいスレッドで、関係する依頼の要求の末尾にその事実が付く。
## 効果の実測：関連する課題を続けて解く（プロジェクト内の実測、2026-11-19）

- 設計：
  - Linux カーネルで、同じ関数 F について「F の呼び出し元」→「その呼び出し元の呼び出し元（2 段）」を続けて解く。`tasks-hard.json` の 2 段の課題 15 問から作った 15 組（`refs/kernel-bench/tasks-chain.json`）。
  - M：自動記録ありの main（33083e3）。N：同じソースで記録だけを止めた実験用のビルド（コミットしていない）。
  - 記憶は版ごとに別の保存先に、15 組を通して溜めた。
  - Claude OAuth の `claude-haiku-5-5`、各 1 回、課題ごとに M・N を交互に実行。60 ターンすべて完了、再試行 0 回。
  - 結果は `refs/kernel-bench/runs-chain/`、集計は `chain_score.py` と `summary-chain.json`（git 管理外）。
- 結果（組ごとの差の Wilcoxon、15 組。中央値）：

| 正答（F1、平均） | 0.993 | 0.993 | 差なし | 0.974 | 0.971 | 0、p = 0.32 |
| 入力トークン | 17,004 | 11,888 | +8,083、p = 0.026 | 25,958 | 16,909 | +5,445、p = 0.055 |

- 保存された事実（M、93 件）：
  - 89 件はツールの振る舞い（`find` の出力は区切りがバックスラッシュ、結果は 50 件まで、など）。同じ内容がほぼ毎ターン、言い方を変えて保存された。題名の完全一致による重複の除外は効かなかった。
  - 2 問目に役立つはずの「F の呼び出し元」は保存されなかった。指示で「課題の答え」を除外したため。
- 読み方：
  - 正確さは変わらず（上限に近い）、作業の手数も減らなかった（2 問目の要求回数の差は記録の 1 回分）。
  - 費用は増えた：記録の要求で 1 ターンあたり出力が約 2〜3 千トークン、時間が約 12 秒増えた。
  - この形の自動記録は、この条件では効果がなく、費用だけがかかった。
- 限界：モデル 1 つ、各 1 回、15 組。課題は易しく、正答は上限に近い。プロジェクトは 1 つ。
