## プロジェクト内の観察：指示しないと使われない

- カーネルの実験 335 ターン（`refs/kernel-bench` の `runs-comp`・`runs-limit`・`runs-hard`・`runs-cd`、Haiku 5.5）のツール呼び出し：
  - `find` 2,523、`read` 1,389、`shell` 125、`plan` 4、`lesson` 1、`search` 1、`recall` 0。
  - これらの課題は読むだけの 1 ターンの課題で、記憶のツールが要らなかった可能性もある。

- 結論（観察）：ツールの説明文だけでは、新しいツールはほとんど使われない。

### プロジェクトをまたぐ共有

- 共有と同じプロジェクト内とを分けて比べた研究は見つからなかった。
- Wang et al., MemGovern, arXiv 2601.06789（査読前）：GitHub の人の記録から作った経験カード 135K 枚で +2.4〜9.4 ポイント（8 モデル）。**トークンと費用はすべてのモデルで増えた**（Kimi-K2 では費用が 2 倍）。加工しない記録の効果は不安定。
- CTIM-Rover：リポジトリ単位の教訓（31%）は一般の教訓（36%）より悪かった（45 問）。

### 根拠の照合（ハルシネーション対策）

- コーディングエージェントの中で、引用を出典の本文と照合する仕組みの効果を測った研究は見つからなかった。
- Magesh et al., J. Empirical Legal Studies 22(2), 2025（査読あり）：出典を取り出してから答える法律調査ツールでも、17〜33% は作り話を含んでいた（数値は二次資料）。取り出すだけでは防げない。
- Jain et al., ICSE 2025 SEIP（査読あり）：API の文書を渡すと、あまり使われない API の正しい呼び出しが 38.58% → 47.94%。**取り出しが悪いと、よく使われる API で 39.02 ポイント悪化**。必要なときだけ取り出すと +8.20。
- Kim et al., HALLMARK, arXiv 2607.18360（査読前）：規則による確認の後に LLM を使うと、検出 0.990・誤検出 0.037。LLM だけでは誤検出 0.478。
- Rao et al., arXiv 2604.03173（査読前、要旨のみ）：URL を確かめる道具を渡すと、存在しない URL が 1% 未満に減った。中身が主張を支えるかは確かめていない。
- Liu et al., "Who Checks the Citations?", arXiv 2606.21155（査読前、要旨のみ）：最良の確認役（GPT-5）でも、法律の引用の誤りの再現率 84.4%・F1 55.0%。

### トークン費用

- ツールの数：LongFuncEval（arXiv 2505.10570、査読前）で、ツールの一覧が 49 → 741 個に増えると正答が 7〜85% 下がった。RAG-MCP（arXiv 2505.03275、査読前）は、必要なツールだけ渡すとプロンプトが半分以下、選択の正答 13.62 → 43.13%。
- キャッシュ：Lumer et al., "Don't Break the Cache", arXiv 2601.06007（査読前）：キャッシュで費用 41〜80% 減。変わる内容までキャッシュに含めると、かえって遅くなることがある。システムプロンプトだけをキャッシュするのが最も安定。
- 長い会話での指示の劣化：Laban et al., ICLR 2026：複数ターンで平均 39% 低下。最後にまとめ直しても完全には戻らない。

## 調査からの読み取り（推測。研究の結論ではない）

1. **効果は小さく、条件つき。** コーディングでは、強いモデルで +1〜5 ポイント程度。手数は減るが、トークンは増えることが多い。
2. **選別しない記憶は害になる。** エージェントが自分で書いただけの記憶は、効果なしか悪化（SkillsBench、SWE-ContextBench、VibeMemBench、CTIM-Rover）。検証済みのものだけ使うと効く（VibeMemBench、MemGuard）。
   - inocode の「候補 → 有効」の設計（`project-memory.md` の判断 7）はこれに合う。
3. **出すのは 1 件に絞る。** 2 件以上で下がる（SWE-Exp）、無関係なものが誤らせる（CTIM-Rover、Jain et al.）。
4. **使わせるには、ツールを置くだけでは足りない。** プロジェクト内でも研究でもそうなっている。ハーネスが差し込む方式のほうが、根拠がある（Proactive Memory Agent。ただし査読前で差は小さい）。
5. **根拠台帳は、機械で確かめられる部分だけが確実。** URL が存在する、引用した文が取得した本文にある、という確認。中身が主張を支えるかの判定は、LLM でも誤りが多い。

## 設計案（承認待ち）

| 案 | 内容 | 根拠 | トークンへの影響（推測） |
|---|---|---|---|
| 1 | 記憶はハーネスが差し込む。モデルに検索を任せない。合うものを最大 1 件、有効なものだけ、最新の発言の直前に置く | Proactive Memory Agent、SWE-Exp（1 件）、`project-memory.md` 判断 15（Lost in the Middle） | 差し込む分（数百トークン）が毎回増える。キャッシュの後ろに置くので、前の部分のキャッシュは壊さない |
| 2 | モデルが書いた教訓・手順は候補のまま。テストが通った、または人が承認したものだけ有効にする | SkillsBench、VibeMemBench、MemGuard、Xiong et al. | 書く呼び出しの分だけ増える |
| 3 | システムプロンプトに、記憶のツールをいつ使うかを数行書く（固定の文で、キャッシュされる） | プロジェクト内の観察（5/281 → 61/80）。Gloaguen et al. は指示で費用が増えると報告 | 固定の数行。キャッシュに入る。手数が増える可能性があるので測る |
| 4 | 書くツールは 1 つにまとめる（種類を引数で選ぶ）。ツールの一覧は変えない | LongFuncEval、RAG-MCP、Lumer et al.（キャッシュ） | ツールの定義 1 つ分 |
| 5 | 根拠台帳は、URL の存在と、引用した文が取得本文にあるかだけをハーネスが確かめ、通ったものを「検証済み」にする。中身の判定は人 | HALLMARK、urlhealth、Magesh et al.。コーディングでの研究はない | `fetch` の結果を照合するだけで、モデルは呼ばない |
| 6 | 規則（`ask`・`block`）を人が登録する手段 | AgentSpec（`agent-tools.md`） | なし（ハーネス内の判定） |

- 共有の範囲：分けて比べた研究がないため、プロジェクト内を既定とし、共有は人が選んだものだけにする案。
- 効果の確かめ方：記憶が効くかは 1 回の課題では測れない。同じリポジトリで関連する課題を順に解かせ、記憶あり・なしを比べる実験が要る（SWE-ContextBench の方式）。設計は未定。
