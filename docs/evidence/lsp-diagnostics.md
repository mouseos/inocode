# 編集の後の型検査・LSP の診断（調査のみ）

- **対象と範囲：** モデルがファイルを編集した後に、言語サーバー（LSP）や型検査を走らせ、診断（型の誤り、未解決の名前）をモデルに返すこと。いまの inocode は、tree-sitter で構文の誤りが増える編集を断るだけ（`edit-write.md`）。
- **関連コード：** main には未実装。ベンチ用の試作は実験用ブランチ `exp/lsp-diagnostics` だけにある（下の「ベンチ結果」）。
- **根拠の状態：** UNSUPPORTED_PENDING。適用できる研究は見つからなかった。ユーザーの指示「３番は根拠あれば作って」（2026-11-21）に従い、実装していない。2026-11-27 のベンチでも効き目は確かめられなかった（下）。
- **ユーザーの判断：** 2026-11-21「さっきの候補1番作って2番も作って3番は根拠あれば作って」。

## 研究（2026-11-21、サブエージェントが原文を読み、報告）

- SWE-agent（NeurIPS 2024、arXiv 2405.15793、表 3）：編集のたびに flake8 で構文・未定義の名前・字下げ（F821・F822・F831・E111〜E113・E999・E902）を調べ、誤りがあれば編集を取り消して見せる。SWE-bench Lite で 18.0%、検査なしで 15.0%。型検査ではない。元のコードに誤りがない前提で、新しい誤りだけを選ぶことはしていない。
- 型で縛る生成（Type-Constrained Code Generation、PLDI 2025、arXiv 2504.09246）：生成された TypeScript のコンパイルの誤りの約 94% は型の誤りで、構文だけの制約は誤りを 9.0%・4.8% しか減らさない。ただしモデルのトークンの確率に手を入れる方式で、API のエージェントには使えない。関数単位の課題。
- Monitor-Guided Decoding（NeurIPS 2023）：LSP で型の合う識別子に絞る。同じく生成の途中に手を入れる方式。
- CodeAgent（ACL 2024、表 5）：書式の検査を外すと −1.0、記号の移動（定義へ飛ぶなど）を外すと −7.9。
- CoCoGen（arXiv 2403.16792）：コンパイラの誤りだけを返しても +1.18 ポイントと小さく、効いたのは誤りに関係する文脈を取ってくること。
- FeedbackEval（arXiv 2504.06939、査読前）：1 回の修正で、pylint の出力（34.9%）は 1 行の手がかり（43.5%）より悪かった（SWE-bench Verified の 178 件）。
- openJiuwen（arXiv 2608.27969、査読前）：LSP の診断を返す仕組みを持つが、その部分を外した比較はない。
- 唯一の直接の比較（"When Do Language Servers Help Coding Agents?"、GitHub の報告、査読なし）：Qwen2.5-Coder-7B と Pyrefly、14 の作られた課題で、編集のたびの診断は 0.440 → 0.494（信頼区間が 0 を含む）。「診断をすべて直してから進め」と指示すると 0.310 に下がった（有意）。提出の時点で型検査を通るまで止める方式では、欠陥を受け入れた数が 11/12 → 1/12（12 組だけ）。
- ほかのハーネス（ソースで確認）：OpenCode は編集の後に LSP の誤り（重大度 1、1 ファイル 20 件まで）を返す（効果の測定は公開していない）。Aider は既定で flake8 の構文・未定義の名前を調べる（効果の数値はない）。Codex には見当たらない。

## 結論（推測を含む）

- 編集のたびに型・LSP の診断を返すことが、エージェントの成功を上げるという査読あり・査読前の研究はない。
- 作るなら考えられる形（未検証）：誤りだけ、件数に上限、編集で増えた誤りだけ、ファイルが構文として通ってから、「全部直せ」とは言わない。ターンの終わりに型検査を通るまで止める方式は、査読なしの小さな報告でだけ強い結果が出ている。
- 費用：サーバーの起動（OpenCode の上限 45 秒）、編集ごとに数秒、途中の編集での誤検出、元からある誤り。

## ベンチ結果（2026-11-26〜27、実測）

**結論：入れない（推奨）。** 30 課題 × 3 回で、型検査の新しい誤りを返しても、解けた数は増えなかった（A 86/90、B 85/90、C 85/90、どの比べも p = 1.0）。Haiku 5.5 は返さなくても ほぼすべて解いており、効く余地がほとんどなかった。費用（1 編集あたり約 2 秒）と、一部の課題での的外れな誤りの表示が残る。

### 試した動き（実験用ブランチ `exp/lsp-diagnostics` だけ。main には入れていない）

- **A：** いまの inocode のまま。
- **B：** `edit`・`edits`・`write` が成功するたびに、プロジェクト全体で型検査を走らせ、その呼び出しの前には無かった誤りだけを道具の答えの後ろに足す。
  - 型検査：Rust は `cargo check --message-format short`、TypeScript はプロジェクトの `node_modules/typescript/bin/tsc --noEmit --pretty false`、Python は `pyright --outputjson`。
  - 誤り（error）だけ。警告は出さない。
  - 「新しい」の判定：ファイル・誤りの番号・文で比べ、行番号は比べない（行がずれても同じ誤りとみなす）。同じ誤りが増えた分は数える。
  - 編集の前の状態：前回の検査からファイル（大きさと更新時刻）が変わっていなければその結果を使い、変わっていれば編集の前に検査し直す。
  - 足す文の形：`cargo check after this change: 2 new errors:` の後に誤りを 1 行ずつ、20 行まで（超えた分は `(N more)`）。「全部直せ」とは書かない。新しい誤りが無ければ何も足さない。検査が動かなかったときも何も足さない。
- **C：** B に加えて、ファイルの削除を断る。スレッドの最初の道具の呼び出しの時点でプロジェクトにあったファイルを覚えておき、どの道具の呼び出しの後でも、それが消えていたら最新の中身で書き戻し、答えに「削除は許されていない、戻した」と足す。後から作ったファイルは消してよい。
- 切り替えは環境変数 `INOCODE_EXP_LSP`（B・C）と `INOCODE_EXP_NODELETE`（C）。実験用ブランチだけにあり、main の動きは環境変数で変わらない。

### 作り

- **モデル：** Claude Haiku 5.5（`claude-haiku-5-5`）、Claude のサインイン経由。ほかのモデルは使っていない。
- **課題：** 公開リポジトリの本物のコミット。直す前のコミットのファイルを渡し、問題を issue の形の英文で伝える（新しい公開 API が要るときは名前と型も書く。どこを直すかは書かない）。コミットで足された・変わったテストのファイルは見せず、終わった後に入れて走らせ、通れば「解けた」。直す前は落ち、コミットの後は通ることを全課題で確かめた。
- **最後に使った 30 課題**（Rust 10、TypeScript 10、Python 10）：
  - Rust：apache/datafusion-sqlparser-rs（3）、tafia/quick-xml（2）、ISibboI/evalexpr、RazrFalcon/roxmltree、pulldown-cmark/pulldown-cmark、dtolnay/semver、Ethiraric/yaml-rust2。
  - TypeScript：unjs/citty（2）、unjs/hookable（2）、supermacro/neverthrow（2）、ianstormtaylor/superstruct、tinylibs/tinybench、unjs/defu、unjs/ufo。
  - Python：pallets/click（2）、pypa/packaging（2）、marshmallow-code/marshmallow（2）、dgilland/pydash、konradhalas/dacite、python-poetry/tomlkit、tkem/cachetools。
  - 課題の一覧（コミット、テストのコマンド、問題文）は `refs/lsp-bench/tasks/`。
- **回数：** 30 課題 × 3 条件 × 3 回 = 270 回。乱数の種は API に無いので、同じ設定を 3 回くり返した。1 回の上限は 25 分（超えたら止めて、その時点のファイルで採点）。3 本ずつ並行。
- **環境：** Windows 11。全条件でサンドボックスなし・承認なし（`full` モード）。課題ごとのビルドの置き場（`CARGO_TARGET_DIR`）はエージェントと型検査で共有。Python はすべての課題で 1 つの venv。

### 調整した理由（設計からの変更）

- 最初の 42 課題（Rust・TypeScript・Python 各 14。変更が数行〜数十行の小さな修正）を A で 1 回ずつ試すと、42/42 すべて解けた。差の出ようがないので、より大きな 24 課題（各 8。2〜6 ファイル、40〜140 行ほど、新しい列挙の値・欄・関数の形の変更を何か所にも通す必要があるもの）を足した。
- その 24 課題を A で 1 回ずつ試すと 22/24（落ちた 2 つのうち 1 つは、同じリポジトリの課題が同じビルド置き場を同時に使ったための採点の誤りだった。ビルド置き場を課題ごとに分けて直した）。
- 本番は、大きい 24 課題と、最初の 42 課題から各言語 2 つずつ（6 課題）の 30 課題にした。最初の課題を減らしたのは、全部解けて差が出ない課題に時間とトークンを使わないため。どの課題を残すかは A の試しの結果を見て決めた（全条件に同じ課題を使うので、条件どうしの比べには偏りは入らない）。

### 読み取り（推測を含む）

- Haiku 5.5 は、型検査の誤りを返さなくても、自分で `cargo test`・`tsc`・`pytest` を走らせて途中の誤りを直していた（A の 1 回あたりシェル 23.6 回）。返した誤りの大半は、エージェントが次の手で直すはずの途中の状態だった（実測の数から、意味の判断は推測）。
- そのため、成功の数でも、要求の数・トークン・時間でも、B・C は A と変わらなかった。B は出力トークンが 1 回あたり約 11% 多かったが、時間や要求の数は増えておらず、差に意味があるかは分からない（推測）。
- 落ちた課題（quick-xml、roxmltree）は、型の誤りではなく、振る舞いの誤りや時間切れで落ちた。型検査の誤りを返す仕組みが救える種類の失敗ではなかった（失敗の記録を読んでの推測）。
- 推奨の理由：解ける数が増える兆しが無く、毎編集に約 2 秒かかり、型の推論が弱いコード（pydash）では的外れな誤りを何十行も返す。研究の状態（直接の根拠なし）も変わらない。もっと弱いモデルや、型の誤りが多く残る課題なら違う結果になりうるが、それは測っていない。
- 「当てはまる研究」の査読なしの報告（Qwen2.5-Coder-7B で +0.054、信頼区間が 0 を含む）とも矛盾しない。強いモデルではさらに効く余地が小さい（推測）。

### 限界

- モデルは Haiku 5.5 の 1 つだけ。課題は 30、各条件 90 回なので、10 ポイント未満の差は見分けられない。A がすでに 96% 解いていて、上がる余地は 4 ポイントしかなかった。
- 課題は小さなリポジトリだけ。大きなリポジトリでは、型検査の時間も、元からある誤りの数も違う。
- 本番に残す課題は A の試しの結果を見て選んだ。
- 25 分の上限で止めた回が 14 回あり、そのうち 10 回は解けていなかった（quick-xml 6、roxmltree 4）。Rust の大きな課題は、3 本並行で同じ機械のビルドを奪い合うので、時間がのびた。
- 全条件でサンドボックスを切った（課題ごとのビルドの置き場がプロジェクトの外にあるため）。いつもの inocode の設定とは違う。
- 型検査はコマンドを毎回走らせる方式で、言語サーバーを起動し続ける方式ではない。Rust の `cargo check` はテストのコードを調べない（テストを含めると、誤りの数と時間は変わる）。
- 誤りが「的外れ」かどうかは、返した行と、その回の終わりの状態・テストの結果から分類した。人が全部の行を読んで判断したわけではない。
