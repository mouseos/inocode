## 提案（承認待ち）

研究で支持され、かつ 5 つのハーネスの多くが持つものから選ぶ。ツールの数は少なく保つ（DATE 2025、RAG-MCP）。

1. `read`
   - 行番号つきで、範囲（offset・limit）を指定して読む。
   - 一度に返す量の上限は未決。SWE-agent の 100 行（研究）と、ハーネス共通の 2,000 行・50KB（公開実装）のどちらにするか。
2. `edit`
   - 完全一致の文字列置換。一致しない、または一致が複数ある場合は失敗を返す。
   - 編集後に構文検査をして、壊れた編集は書き込まない。言語ごとの検査器が要る（SWE-agent の構文検査）。
3. `write`：新しいファイルを作る、または全体を書き換える。
4. `shell`：コマンドを実行する。時間制限と出力の上限を設ける。値には研究がないため、公開実装の値（120 秒、末尾 50KB）を使う。
5. `find`：glob と grep を 1 つにまとめ、件数に上限を設ける（SWE-agent の上限 50 件、各ハーネスは 100〜250 件）。

入れない（根拠なし、または今は不要）：
- サブエージェント
- LSP
- PTY を保つシェル
- Web ページの取得（別に検討。ZeroSearch には一般のページ取得がない）
- 人に聞くツール（`agent-tools.md` の A で、人がいないときは保留して続ける方針がある）

## シェルの対話操作（2026-11-17 の追加調査）

- ユーザーの指摘：
  - 「continue?」のような確認に Y と答えられないと、自走性が下がる。
  - TUI でカーソル移動や Enter ができないと、自走性が下がる。
  - 出力は末尾だけだと冒頭のエラーを見落とす。全文はログに出して read で読むべき。
  - 長いビルドはバックグラウンドで動かすべき。
- 研究：対話式の端末（PTY・キー入力・画面の取得）と、1 回ずつ実行するシェルを比べた対照研究は見つからなかった。
  - Merrill et al., "Terminal-Bench", arXiv 2601.11868（査読前）
    - 基準のエージェント Terminus 2 は、tmux にキー入力を送って操作する。
    - ハーネス同士の比較はある。例：Claude Opus 4.5 で Terminus 2 が 57.8%、Claude Code が 52.1%。ただしモデル・ハーネス・操作方式が同時に変わるため、操作方式の効果は分からない。
  - "Tmax: A simple recipe for terminal agents", arXiv 2606.23321（査読前）
    - 生のキー入力を送る Terminus-2 は小さなモデルでは壊れやすい、と著者が述べている。ただし対照実験ではない。
    - 例：Qwen 3.5 9B で、著者のハーネス（持続するシェル）49.4、Terminus-2 37.9。
- 公開実装：
  - Codex：`exec_command`＋`write_stdin`。PTY を保ち、途中で返して、後から入力を送れる。
  - DSH：`terminal_*`。持続する端末。
  - Terminus 2：tmux にキー入力を送る。
  - Claude Code・Pi・OpenCode：対話入力はない。
- 状態：UNSUPPORTED_APPROVED（研究なし、ユーザーが承認）。

## シェルの実装（承認済みの設計の具体化。値は工学上の選択で研究なし）

- `shell`：`command` と `wait_seconds`（既定 30 秒、上限 600 秒）。待つ時間を過ぎても止めず、ジョブとして走らせ続けて画面を返す。
- `job`：`id`。`input`（文字）、`keys`（名前つきのキー）、`wait_seconds`、`stop` を指定できる。入力や停止をした後の既定の待ち時間は 2 秒、それ以外は 30 秒。
- 端末の大きさは 40 行 × 120 桁。画面は `vt100` で解釈し、文字の表として返す。
- ログ：
  - 保存先はデータベースの横の `<データベース名>.files/logs/thread-<スレッド>/job-<番号>.log`（既定は `~/.inocode/inocode.files/logs`）。利用者のリポジトリには書かない。
  - ジョブの一覧はデータベースとスレッドの組ごとに分ける。1 つのプロセスで複数のデータベースを開いても、互いのジョブを見たり止めたりしない。
  - 端末の制御文字は除いて保存する。
- 終わったコマンドの返し方：
  - 返すのは終了コード・時間・総行数・ログの場所。
  - 出力が 40 行以下なら全文。それより長ければ冒頭 20 行と末尾 20 行。
  - 1 行は 500 字で切る。
- 進み具合の表示：まだモデルに見せていない終了と、走っているジョブを、毎回の要求の状態メッセージ（`plan` と同じ場所）に載せる。
- 中止：ターンを中止すると、そのスレッドのジョブをすべて止める。待っている間の中止もすぐ効く。
- Windows：PowerShell を ConPTY で動かす。ConPTY は起動時にカーソル位置を問い合わせ（`ESC[6n`）、答えが来るまで止まるので、画面のカーソル位置を返す。
- Linux・macOS：`sh -c` で動かす。
- テスト：`server/tests/turn_tcp.rs` の `commands_run_in_a_terminal_that_can_be_answered`。
  - 短いコマンドが終わること。
  - 確認待ちの画面が返ること。
  - `y` と Enter を送ると終わること。
- 未対応：モデルが答えずにターンを終えたとき、走っているジョブの終了を待って続けることはしない（状態メッセージで次の要求に知らせるだけ）。

## find の高速化（2026-11-17 の調査）

- 手元の実測：Codex のリポジトリ、4,972 ファイル、45.2MB。ripgrep 15.0.0、24 スレッド、NVMe。
  - ファイル名の一覧（.gitignore を考慮）：約 40ms
  - 中身の検索：
    - キャッシュ済みで約 0.3 秒。
    - そのセッションで初めて読むときは 2.2 秒。opencode（11,344 ファイル）では 9.5 秒。
    - OS のキャッシュは空にできなかったので、「初回」は近似。
  - スレッド数による差（キャッシュ済み）：1 スレッドで 1.9 秒、24 スレッドで 0.3 秒
  - 別プロセスを起動するだけで約 17ms かかる。
- 研究：
  - n-gram 索引の比較。Zhang, Deep, Patel, Sankaralingam, PVLDB 18(13), 2025, DOI 10.14778/3773731.3773744（査読あり）。
    - 索引なしの走査に対して、1.13〜7.52 倍の速さ。
    - 32MB の DBLP では、全 trigram の索引で 99 秒が 14.7 秒になった。
    - 対象は読み取り専用のデータ。データが変わるたびに索引を更新する方式は研究されていない、と著者が明記している。
  - Cho & Rajagopalan, "A Fast Regular Expression Indexing Engine"（FREE）, ICDE 2002, DOI 10.1109/ICDE.2002.994755（査読あり）。本文を入手できず、数値は確認していない。
  - IDE の trigram 索引：Iakovlev et al., arXiv 2403.03751（査読前）。
    - 索引は 225〜658MB、初回の作成に 118〜340 秒。
    - 1 回の検索は 0.01〜0.63ms。
    - 全体を走査する方式とは比べていない。
  - SIMD による照合：Wang et al., "Hyperscan", NSDI 2019（査読あり）。PCRE より 24.8〜40.1 倍速い。ただし題材はネットワークのパケット検査。
- 見つからなかったもの：
  - 索引が全体の走査より得になるリポジトリの大きさ（ファイルの更新の手間を含めて）。
  - 検索の速さがエージェントの成功率や費用に与える影響。
  - ファイル名の索引と、フォルダを辿る方式の比較。
- 状態：索引は UNSUPPORTED_PENDING（研究はあるが、エージェントのように頻繁に変わるリポジトリには当てはまらない）。

## find のベンチマーク（プロジェクト内の実測、2026-11-17）

- 対象：
  - Linux カーネル `666539eec` を浅く clone した。97,357 ファイル、1,598MB。ユーザーの指定で、このリポジトリだけを測った。
  - 24 スレッド、Windows 11、Defender は有効。
- 検索：32 種類。中身の検索 26（一致なし 3 を含む）と glob 6。結果の上限は 50 件。
- 比べた方式：
  - A：索引なしで全体を走査する（ripgrep の部品をプロセス内で使う）。
  - B：trigram 索引。変更の検出方法で 2 通りに分けた。
    - B-stat：検索のたびに全ファイルの更新時刻と大きさを調べる。
    - B-notify：OS のファイル変更通知を受けて更新する。
  - C：A に加えて、最初に全ファイルを読んでおく。
- 結果（手順とコードは `refs/find-bench`）：

| | キャッシュ済みの検索 中央値（3 回） | p95 | 1〜3 ファイル編集＋検索 2 回 ×50 回 | 古い結果 | メモリ |
|---|---|---|---|---|---|
| A 走査 | 99〜192ms | 866〜906ms | 57〜59 秒 | 0 | 追加なし |
| B-stat 索引 | 432〜453ms | 664〜760ms | 37〜45 秒（作成 3 秒は別） | 0 | +777MB |
| B-notify 索引 | 62〜70ms | 242〜312ms | 2.4〜2.8 秒（作成 3 秒は別） | **50 回中 3〜5 回** | +777MB |

- 結果の正しさ：B は全 32 種類で A と完全に一致した（上限なしで比べた）。
- 初回（新しくコピーした、まだ読んでいないファイル）：
  - A、B の作成、C の事前読み込みは、どれも約 60 秒かかった。
  - 2 回目以降は 1 秒未満になる。初めて開くファイルを Defender が検査していると推測するが、確かめていない。
- B-notify：
  - 編集の直後に検索すると、変更の通知がまだ届いておらず、古い結果を返す。
  - 新しく作られたファイルや、`.gitignore` の変更は拾わない。
- 限界：
  - リポジトリは 1 つ、マシンも 1 台。
  - OS のキャッシュは空にできなかった。

## find の設計の研究（2026-11-17 の追加調査）

- 検索ツールを外す分解実験で査読ありなのは、今も LocAgent（ACL 2025）と SWE-agent（NeurIPS 2024）だけ。

  - 検索の種類：文字列、正規表現、あいまい検索、大文字小文字の区別。

- 設計への示唆（査読前を含む）：

## find の実装（承認済みの設計。値は工学上の選択）

- 方式：索引なしの走査（上のベンチマーク）。
  - ripgrep の部品（`ignore` の並列走査、`grep-searcher`、`grep-regex`）をプロセス内で使う。
  - `.gitignore` に従う。バイナリのファイルは飛ばす。
- 引数：
  - `pattern`：既定は文字列。`regex` が true なら正規表現。`ignore_case` で大文字小文字を区別しない。
  - `name`：定義の名前の完全一致。その名前を含むファイルだけを構文木とハイライト用の文法で解析する（`core/src/outline.rs`）（LocAgent の名前検索）。
  - `files`：glob。単独なら、ファイル名の一覧を返す。
  - `path`：探すフォルダ。
- 出力：`path:行: 本文`。
  - パスと行の順に並べる（並列走査の順序に左右されないように）。
  - 最初の 50 件を出し、総数を示す。50 件を超えたら絞り込みを求める（SWE-agent の上限）。
  - 1 行は 300 字で切る。並べ替えのために保持する結果は 10,000 件まで。総数はすべて数える。
- テスト：`find.rs` の単体テスト。
  - 文字列と正規表現、大文字小文字の区別、glob で絞ること。
  - `.gitignore` の対象を除くこと。
  - 名前検索が呼び出しではなく定義だけを返すこと。
  - ファイル名の一覧、50 件の上限、一致がない場合。

- 2026-11-17：シェルの設計を承認（「研究がなくても止まることは確実だ。採用して」）。承認した内容：
