## 設計（承認済み）

1. **規則を 1 件ずつ持つ：** ID、本文（原文のまま）、出典（ファイルと行、見出しの階層）、強さ、版。
   - **強さ「必須」：** 機械で判定できるもの。例：承認なしの push、非公開アドレスの書き込み、コミット作者のメール。ハーネスがツール実行の直前に判定し、止める・確認を求める。根拠は AgentSpec。
   - **強さ「推奨」：** 判断を要するもの。関係するものだけを判断の場面で提示する。逸脱は可能だが、理由を根拠台帳に残させる。根拠は指示の数の研究と、会話中の劣化。全部を常に入れることはしない。
2. **適用の記録はハーネスが書く：** どのターンでどの規則を提示したか、どのツール呼び出しで判定し、止めたか・許したか・人が承認したか。モデルが「この規則に従った」と書いた内容は、「モデルの申告」として区別して残す。根拠は Turpin et al.。
3. **既存文書からの取り込み：**
   - AGENTS.md / CLAUDE.md を見出しと箇条書きで機械的に分割し、本文は言い換えずに取り込む（情報を落とさない）。
   - ファイルのハッシュが変われば取り込み直し、変わった規則は旧版を残して置き換える。
   - 「必須」への変換（判定条件の作成）は LLM に候補を作らせてよいが、人の承認で有効にする。根拠は AgentSpec の LLM 生成の再現率 70.96%。
   - コードベースから規則の文章を自動生成することはしない。根拠は Gloaguen et al.（LLM 生成のファイルはわずかに悪化）。
4. **ローカル issue：** 保存層のノートに「issue」の種類を加える。状態（未着手・作業中・保留・完了・見送り）、優先度、依存（何が何を止めているか）、関連する教訓・主張・会話へのリンクを持つ。会話の開始時に、未完了の上位数件だけを短く示す。会話内の計画（todo）とは別物で、会話をまたいで残る。
5. **規則と issue は既存のノートの仕組みを使う：** 全文検索・タグ・リンク・版・連想を新たに作らない。規則の適用記録と issue の状態変化は、1 つのイベント表に時刻つきで残す。

## モデルによる分割（追加の承認による）

見出しと箇条書きだけでは、1 つの項目に複数の規則が入る、段落に規則と理由が混ざる、親と子の項目で 1 つの規則になる、といった文章を規則 1 件ずつに分けられない（ユーザーの指摘）。そこで次のようにした。

1. 機械で見出しごとの節に分け、節の本文を「単位」（文と行。`。` `！` `？` と、後ろに空白が続く `.` で文を切る）に分けて番号を振る。モデルには番号つきの単位を渡し、規則・理由・その他を**番号だけ**で答えさせる。題名・条件・キーワードはモデル自身の言葉で、検索の入口にだけ使う（ノートの title・condition・keywords）。
2. 規則の本文（body）と理由（summary）は、番号の指す原文の範囲をそのまま切り出す。連続する番号は原文の 1 区間（書式記号や改行を含む）として切り出し、離れた区間は改行でつなぐ。モデルは本文を書かないので、言い換えも書式の脱落も起こらない。
3. ハーネスの検査：存在しない番号、規則がない、番号のない規則、JSON でない応答、接続の失敗、32 KiB を超える節は、その節だけ機械的な分割に戻し、理由を `ImportReport::fallbacks` で返す（次回の取り込みで再びモデルへ送る）。どこにも割り当てられなかった単位（記号・番号・句読点だけのものは除く）は `ImportReport::unassigned` で返す。
4. 節ごとに本文の SHA-256 を `rule_sections` に保存し、変わらない節は再送しない。変わった節では、本文が同じ規則を残し、新しいものを追加し、残りを退役させる。消えた節の規則は退役させる。各規則がどちらで分けられたかを `rules.segmented_by`（`model` / `mechanical`）に残す。
5. 節は最大 4 つまで並行して送る。

### 実通信の結果と、引用方式から番号方式への変更

最初の実装は、モデルに原文を一字一句引用させ、引用が原文にあるかを検査していた。2026-11-16、Logfare（`logfare/auto`、既定の思考 medium）でこのリポジトリの AGENTS.md を取り込んだ結果（ユーザーの許可を得て実施。1 回目は行番号計算の不具合（複数バイト文字の途中でのスライス）で途中終了し、修正後に再実行）：

- 所要 538 秒（節を 1 つずつ送っていた）、規則 43 件、割り当てのない断片 0。
- 8 節のうち 4 節が機械的な分割に戻った。原因は 2 種類：モデルがプロンプトの見出し行（`Section: …`）を引用した、モデルが `**…**` などの書式記号を落として引用した（一字一句の検査で拒否）。

いずれも「モデルに原文を書き写させる」ことが原因なので、番号で答えさせる方式に変えた（言い換え・書式の脱落が原理的に起きず、出力も短い）。同時に節を並行して送るようにした。番号方式での実通信は未実施。

## 実装上の判断（このプロジェクトの判断）

- 取り込みの単位：見出しで節を決め、箇条書きの項目（入れ子も 1 件ずつ）、段落、コードブロックをそれぞれ 1 件にする。本文は言い換えず、前後の空白だけを除く。題名は最初の行の先頭 80 文字。
- 取り込み直しの照合：ファイル・節・節内の順番の組で同じ規則とみなす。本文が同じなら残し（行番号だけ更新）、違えば新しい版で置き換えて旧版を残し、なくなった規則は退役させる。順番の組で照合するため、途中に項目を挿入すると後続の項目は「変更」として扱われる（旧版は残る）。
- 取り込んだ規則と人が直接書いた規則は「推奨」で始まる。「必須」にするには、判定条件（対象のツール名または `*`、引数に含まれる文字列のいずれか、処置＝止める／確認を求める）を提案し、人が承認する。判定は部分文字列の一致だけ（正規表現は使わない）。止める規則が 1 つでもあれば止める。発火した規則は、それぞれ自分の処置（`blocked` / `asked`）で記録される。
- 記録の主体は `harness`（提示・判定）、`person`（承認・状態変更）、`model`（逸脱の理由、従ったという申告）を区別して残す。
- issue の状態は open / in_progress / blocked / done / wontfix、優先度は 0 が最も急ぐ。「止めている」関係はリンク（`blocks`）で持ち、完了・見送りになった issue はもう止めていないものとして扱う。
