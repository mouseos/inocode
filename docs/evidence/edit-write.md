# edit・edits・write の道具と、効率化の候補

- **対象と範囲：**
  - `edit`：既存の文書ファイルの一部を、完全一致の文字列で置き換える。
  - `edits`：`edit` と同じ置き換えを、1 回の呼び出しで複数（複数のファイルにも）。全部か、何もしないか。
  - `write`：ファイル全体を書く（新規作成または置き換え）。
  - 効率化・正確さの改善の候補は、調べて下にまとめた。実装したのは、空白を無視した照合と、編集後の構文検査。
- **関連コード：** `core/src/edit.rs`。登録は `core/src/agent_tools.rs`。パスの解決は `core/src/read.rs` の `resolve` を共有する。
- **根拠の状態：**
  - 置換形式（search/replace）を使うこと：RESEARCH_SUPPORTED。
    - Diff-XYZ（査読前、`harness-tools.md`）。
    - Wang et al., "Cascaded Code Editing", FSE 2026（査読あり）。
  - 完全一致で、一致が 0 件や複数件なら断ること：RESEARCH_SUPPORTED（査読前 1 件、下の表）。
  - 完全一致がないとき、空白を無視して照合し、一意でなければ断ること：RESEARCH_SUPPORTED（同じ査読前 1 件）。
    - 細部は工学上の選択。
      - 行単位で比べる。
      - 字下げの差を新しい行に足す。
      - 空白を無視して一致したことを結果で知らせる。
  - 変更で構文の誤りが増えるなら、書かずに断ること：RESEARCH_SUPPORTED（査読あり 1 件、下の「編集後の構文検査」）。
    - 論文の条件から広げた部分（Python 以外の言語、検査器を tree-sitter にしたこと、`write` にも当てはめたこと）は推測による当てはめで、効果は確かめていない。
  - それ以外の細部（`all` 引数、CRLF の扱い、返す文、フォルダの自動作成）：UNSUPPORTED_APPROVED。工学上の選択で、ユーザーの承認による。
  - `edits`（一括編集）：UNSUPPORTED_APPROVED（下の「一括編集」）。形式は上の置換形式と同じで、その部分の根拠は上と同じ。まとめることで往復やトークンが減るか、全部か何もしないかの扱いがよいかは、研究がない。

## 一括編集（`edits`、2026-11-20）

- 形式：`edits` の配列。各要素は `edit` と同じ `path`・`old`・`new`・`all`。行番号は使わない。
  - 根拠（2026-11-20、サブエージェントが原文を読み、報告）：Diff-XYZ（arXiv 2510.12487、査読は未確認）の表 5 で、差分の生成の完全一致は置換形式が最もよく（GPT-4.1 で 0.95、unified diff 0.81、行番号を除いた unified diff 0.69）、行番号を使う形式は悪かった。著者は、置換形式は各編集が独立しているので、1 つの誤りがほかを無効にしないと説明する。限界：道具を使わない代理の課題、推論モデルなし。
  - SWE-agent（NeurIPS 2024、表 3）：編集の道具がないと 10.3%、構文検査ありの編集で 18.0%。1 回失敗した後の編集は、成功が 57.2% に下がる（5.2 節）。
- 動作：順に、前の置き換えが残した文に当てる（同じファイルへの複数の置き換えも順に）。すべて当てはまり、どのファイルにも構文の誤りが増えないときだけ書く。1 つでも失敗したら、どのファイルも変えず、何番目のどのファイルで、なぜ失敗したかを返す。
  - 全部か何もしないかにしたのは工学上の選択（研究なし）。OpenAI の apply_patch の参考実装も、書く前にパッチ全体を確かめる（公式の文書、研究ではない）。
  - 書き込みの途中で失敗した場合（ディスクの誤りなど）は、すでに書いたファイルを返す。書き込みそのものは取り消せない。
- 承認：`edit` と同じく変更として扱う（`ask` では人の承認を待つ）。
- 検証：単体テスト `edits_are_made_all_together_or_not_at_all`（2 つ目の失敗で何も書かれないこと、構文の誤りで別のファイルも書かれないこと、同じファイルへの置き換えが順に当たること、空の配列、ないファイル）。実際のモデルでの効果は未検証（ベンチマークは完成後）。

## 実装

- `edit`：引数は `path`・`old`・`new`・`all`（既定 false）。
  - `old` がちょうど 1 回現れるときだけ置き換える。0 回なら「現れない」、複数回なら回数を返して断る。`all` が true なら、すべて置き換える。
  - `old` が空のとき、`old` と `new` が同じときは断る。
  - CRLF のファイル：`read` は `\r` を除いて見せるので、モデルは `\n` で書いてくる。そのまま一致しないときは `old`・`new` を `\r\n` に直して照合し、書き込む。
    - これがないと、Windows の改行のファイルは一切編集できない。
  - NUL を含むファイル、UTF-8 でないファイルは断る。
  - 返すもの：置き換えた回数と、最初の置き換えの行番号。
  - 空白を無視した照合（完全一致が 0 回のときだけ）：
    - 比べ方：`old` の各行と、ファイルの連続する行を比べる。前後の空白を除き、行の中の連続する空白を 1 つにしてから比べる。
      - 行の一部だけの `old` は、この方法では一致しない。
    - 一致した範囲が 1 つなら、その行全体を `new` で置き換える。
      - 2 つ以上なら、`all` が true でも断り、回数を返す（論文の「あいまいなら断る」）。
    - 字下げ：一致した行のどれも、`old` の行より同じ文字列だけ深く字下げされていれば、`new` の空でない行にもその文字列を足す。そろっていなければ `new` をそのまま入れる。
    - 改行：ファイルの改行（LF か CRLF）に合わせる。
    - 結果の文で、空白を無視して一致したことと、字下げを確かめるよう伝える。
- `write`：引数は `path`・`content`。
  - 足りないフォルダは作る（Pi と同じ）。既存のファイルは置き換える。
  - 返すもの：作成か置き換えかと、行数。
  - 置き換える前に読んだかは確かめない（下の「入れなかったもの」）。
- 編集後の構文検査（`edit`・`write` の両方。`edit.rs` の `new_syntax_errors`、`outline.rs` の `syntax_errors`）：
  - 対象：`outline.rs` に tree-sitter の文法がある言語（Rust、Python、JavaScript、TypeScript、TSX、Go、Java、C、C++。拡張子で決める）。それ以外のファイルは検査しない。
  - 変更後の内容を構文解析し、誤りの節点（ERROR と MISSING）を数える。変更前の内容（新しいファイルなら 0）より増えたら、ファイルを書かずに断る。
    - もとから誤りのあるファイルは、誤りを増やさない限り編集できる。SWE-agent は元のコードが正しいと仮定しているが、inocode では作業途中のファイルもあるため。
  - 断るときに返すもの：変更前後の誤りの数、誤りの行、最初の誤りの前後の行（変更後の内容で）、「直して送り直す。同じ変更は同じように失敗する」。SWE-agent の Figure 11 の文面（誤りの種類、変更後の行を示す、同じ編集を繰り返さないよう伝える）にならった。
- 規則（`agent-tools.md` の禁止・保留）は、ほかのツールと同じように呼び出しごとに検査される。
- テスト：`edit.rs` の単体テスト。
  - 一致が 1 回、複数回、`all`、一致なし、空、同じ文字列の場合。
  - CRLF のファイル。
  - 空白を無視した照合：
    - 字下げの差を足すこと。
    - 行の中の空白、CRLF、末尾に改行がないこと。
    - 行の削除。
    - 2 回一致したら断ること。
    - 行の一部では一致しないこと。
  - プロジェクトのフォルダでの作成・編集・置き換え。
  - 構文検査：誤りを増やす `edit` と `write` は断られ、ファイルは変わらない。正しい編集は通る。もとから誤りのあるファイルへの、誤りを増やさない編集は通る。文法のないファイルは検査しない。
  - 開けないファイル、NUL を含むファイル、プロジェクトのフォルダがないときの相対パス。

## 編集後の構文検査の根拠（2026-11-20 に原文で確認）

- 出典：Yang, Jimenez, Wettig, Lieret, Yao, Narasimhan, Press, "SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering", arXiv 2405.15793（v3 2024-11-11、DOI 10.48550/arXiv.2405.15793）。https://arxiv.org/abs/2405.15793 。掲載先は NeurIPS 2024 とされるが、今回取得した本文では確かめられなかった。
- 結果（Table 3、5.1 節）：SWE-bench Lite の test（300 件）、GPT-4 Turbo（gpt-4-1106-preview）。
  - 検査あり 18.0%（54 件）、検査なし 15.0%（45 件、論文の % からの計算）、編集の道具なし 10.3%。
  - 差は 300 件中およそ 9 件。繰り返しのばらつきや有意差の検定は示されていない。
- 仕組み（付録 A.1、Table 4、Figure 11）：
  - Python のファイルに flake8 を `--select=F821,F822,F831,E111,E112,E113,E999,E902` で走らせる。未定義の名前、字下げの誤り、構文の誤りを含む。
  - 出力があれば、編集は取り消され、適用されない。モデルには、誤りの一覧、変更後の行、元の行と、同じ編集を繰り返さないことが示される。
- 論文自身が挙げる欠点：「ある程度、編集を特定の順で行うことを強いる」（付録 A.1）。
- inocode との違い（当てはめの限界）：
  - inocode は構文の誤りだけを見る。未定義の名前（F821 など）は見ない。
  - Python 以外にも広げた。検査器は flake8 ではなく tree-sitter。tree-sitter は誤りから回復して解析するので、誤りの数え方は flake8 と同じではない。
  - C・C++ のマクロなど、tree-sitter が正しく読めない書き方では、正しい変更を断ることがありうる。誤りが「増えた」ときだけ断るので、もとからある読めない箇所では断らない。
  - 2024 年のモデル 1 つでの結果。いまのモデルで同じ差が出るかは確かめていない。
- 確認の方法：サブエージェントが arXiv の HTML 版を読み、数値と引用を報告した。E.3 節（限界と今後）は取得できず、未確認。

## 入れなかったもの

- 読んでいないファイルや、読んだ後に変わったファイルの編集を断る確認（Claude Code・DSH にある）。研究の根拠がない。
- 近い行の提示：上の候補。採否はユーザーが決める。
- 未定義の名前の検査（SWE-agent の F821・F822）：言語ごとの解析器が要るので入れていない。
- 人に聞くツール、サブエージェント、LSP、ツール検索：以前の比較（`harness-tools.md`）で入れないとした方針のまま。

## ユーザーの承認

- 2026-11-19：「editツールなど特に高速化や効率化のしようがなさそうなツールすべて実装しておいて。もし効率など挙げられる手法がある場合は調べてまとめておいて。」
  - 承認されたのは、基本の `edit`・`write` の実装。
  - 効率化の手法は調べてまとめるだけで、実装は承認されていない。
- 2026-11-19：空白を正規化した照合を足すかの質問に「足す」。
- 2026-11-20：編集後の構文検査と MCP の受け口の提案に「１と２やって」。
- 2026-11-20：「効率化のしようがないものは実装しちゃって」の後の質問「根拠を調べずに実装してよいものはどれですか？」で「複数か所の一括編集」を選んだ。
