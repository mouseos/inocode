# edit・write の道具と、効率化の候補

- **対象と範囲：**
  - `edit`：既存の文書ファイルの一部を、完全一致の文字列で置き換える。
  - `write`：ファイル全体を書く（新規作成または置き換え）。
  - 効率化・正確さの改善の候補は、調べて下にまとめた。実装したのは空白を無視した照合だけ。
- **関連コード：** `core/src/edit.rs`。登録は `core/src/agent_tools.rs`。パスの解決は `core/src/read.rs` の `resolve` を共有する。
- **根拠の状態：**
  - 置換形式（search/replace）を使うこと：RESEARCH_SUPPORTED。
    - Diff-XYZ（査読前、`harness-tools.md`）。
    - Wang et al., "Cascaded Code Editing", FSE 2026（査読あり）。
  - 完全一致で、一致が 0 件や複数件なら断ること：RESEARCH_SUPPORTED（査読前 1 件、下の表）。
  - 完全一致がないとき、空白を無視して照合し、一意でなければ断ること：RESEARCH_SUPPORTED（同じ査読前 1 件）。
    - 細部は工学上の選択。
      - 行単位で比べる。
      - 字下げの差を新しい行に足す。
      - 空白を無視して一致したことを結果で知らせる。
  - それ以外の細部（`all` 引数、CRLF の扱い、返す文、フォルダの自動作成）：UNSUPPORTED_APPROVED。工学上の選択で、ユーザーの承認による。

## 実装

- `edit`：引数は `path`・`old`・`new`・`all`（既定 false）。
  - `old` がちょうど 1 回現れるときだけ置き換える。0 回なら「現れない」、複数回なら回数を返して断る。`all` が true なら、すべて置き換える。
  - `old` が空のとき、`old` と `new` が同じときは断る。
  - CRLF のファイル：`read` は `\r` を除いて見せるので、モデルは `\n` で書いてくる。そのまま一致しないときは `old`・`new` を `\r\n` に直して照合し、書き込む。
    - これがないと、Windows の改行のファイルは一切編集できない。
  - NUL を含むファイル、UTF-8 でないファイルは断る。
  - 返すもの：置き換えた回数と、最初の置き換えの行番号。
  - 空白を無視した照合（完全一致が 0 回のときだけ）：
    - 比べ方：`old` の各行と、ファイルの連続する行を比べる。前後の空白を除き、行の中の連続する空白を 1 つにしてから比べる。
      - 行の一部だけの `old` は、この方法では一致しない。
    - 一致した範囲が 1 つなら、その行全体を `new` で置き換える。
      - 2 つ以上なら、`all` が true でも断り、回数を返す（論文の「あいまいなら断る」）。
    - 字下げ：一致した行のどれも、`old` の行より同じ文字列だけ深く字下げされていれば、`new` の空でない行にもその文字列を足す。そろっていなければ `new` をそのまま入れる。
    - 改行：ファイルの改行（LF か CRLF）に合わせる。
    - 結果の文で、空白を無視して一致したことと、字下げを確かめるよう伝える。
- `write`：引数は `path`・`content`。
  - 足りないフォルダは作る（Pi と同じ）。既存のファイルは置き換える。
  - 返すもの：作成か置き換えかと、行数。
  - 置き換える前に読んだかは確かめない（下の「入れなかったもの」）。
- 規則（`agent-tools.md` の禁止・保留）は、ほかのツールと同じように呼び出しごとに検査される。
- テスト：`edit.rs` の単体テスト。
  - 一致が 1 回、複数回、`all`、一致なし、空、同じ文字列の場合。
  - CRLF のファイル。
  - 空白を無視した照合：
    - 字下げの差を足すこと。
    - 行の中の空白、CRLF、末尾に改行がないこと。
    - 行の削除。
    - 2 回一致したら断ること。
    - 行の一部では一致しないこと。
  - プロジェクトのフォルダでの作成・編集・置き換え。
  - 開けないファイル、NUL を含むファイル、プロジェクトのフォルダがないときの相対パス。

## 効率化・正確さの候補（2026-11-19 の調査）

| 方法 | 主張 | 査読 | 出典と数値 | 限界 | inocode への当てはめ |
|---|---|---|---|---|---|
| 内容で位置を決める置換と、行番号・範囲・関数名で決める編集の比較 | 内容で決める方式は、失敗するときは断る。位置で決める方式は、黙って別の場所を書き換える | 査読前 | Althoubi, "Look Before You Leap", arXiv 2609.11957。Python 224 ファイル・640 編集・23,040 試行。ファイルの中身をずらした条件で、別の場所を書き換えた割合：完全一致 0.000、空白を正規化した一致 0.000、unified diff 0.000、行範囲 0.991、関数全体 0.127 | 人工的なずらし方。Python だけ。コードは未公開 | 今回の完全一致・断る方式を支持する。行番号で位置を決める方式は採らない |
| 空白を正規化した照合を、完全一致で見つからないときの予備にする（あいまいなら断る） | 成功率が上がり、別の場所の書き換えは増えない | 査読前 | 同上。ずらした条件で、成功率 0.176 → 0.571。最初の一致を採る方式にすると、別の場所の書き換えが 0.023 | 同上 | **実装した**（下の「空白を無視した照合」）。編集の失敗とやり直しの要求が減る見込み。効果は inocode では未測定 |
| あいまいな一致（類似度） | 成功率は高いが、別の場所を書き換える | 査読前 | 同上。1 か所の変更で 0.023、複数か所の変更をまとめると 0.393 | 同上 | 採らない |
| 置換形式・ファイル全体・unified diff の比較 | 置換形式とファイル全体はほぼ同じ。unified diff は正答が低く、トークンも多い | 査読あり（FSE 2026） | Wang et al., "Cascaded Code Editing", DOI 10.1145/3808101、Table 10、Aider のベンチマーク。DS-R1：ファイル全体 35.6（2.6M トークン）、置換 34.7（2.5M）、unified diff 28.4（2.8M） | DeepSeek の 2 モデルだけ | `edit`（置換）と `write`（全体）の 2 つで足りる。unified diff は入れない |
| 置換とファイル全体の書き直しを、編集ごとに選ぶ | 費用が少し下がる | 査読前 | Zhang et al., "SWE-Edit", arXiv 2604.26102。SWE-bench Verified：解決 69.4 → 69.9%、費用 $244.7 → $215.9。この条件では置換の約 20% が失敗した | 選ぶために学習したモデルが要る。100 件・2 回 | モデルが `edit` と `write` を選べるので、道具としては今の形で足りる |
| 編集を別の小さなモデルに任せる（apply model） | 時間と費用が減る | 査読あり（FSE）・査読前 | Cascaded：時間 −17%／−13%、費用 −19%。ただし DS-V3 ではトークンが 357K → 523K に増えた。SWE-Edit：費用 −17.9% | 2 つ目のモデルが要る | 新しい仕組み（範囲外）。未実装 |
| 変わらない部分を写して出力する復号（speculative edits など） | 生成より大幅に速い | 査読前（1 件は取り下げ） | arXiv 2604.18170（取り下げ）、QiMeng-PRepair arXiv 2604.05963（最大 15% 速い） | 推論サーバーを制御できる場合だけ | ホスト型 API では使えない |
| 編集後の構文検査 | 構文の誤りを弾くと成功率が上がる | 査読あり | SWE-agent（NeurIPS 2024）：18.0% 対 15.0%（`harness-tools.md`）。LintEval（Findings of EMNLP 2026、要旨のみ）はリファクタリングの課題 | 2024 年のモデル。言語ごとの検査器が要る | 候補。未実装。`outline.rs` の構文木で、編集前より誤りが増えたら断る方式が考えられる |
| 編集後の LSP 診断 | 効果なし、トークン増 | 査読前 | Xu, arXiv 2608.13568：トークン +6〜+118% | 移動（ナビゲーション）の研究で、編集後の診断ではない | 採らない |
| 読んだ後にファイルが変わっていたら断る | 間接的な動機だけ | 査読前 | SWE-Touch, arXiv 2608.02499：作業中に別の編集を入れると、解決率が 7.7 ポイント下がる | 確認の仕組み自体は試していない | 根拠不足。未実装 |
| 失敗したとき、近い行を返す | 研究なし | — | SWE-Edit で置換の失敗が約 20%。edit-bench（研究ではない）では、失敗の原因は作り話の内容や、貼り付けた行番号 | — | 候補。根拠不足 |

- 見つからなかったもの：
  - 1 回の呼び出しで複数の編集をまとめる効果（要求の回数への影響）。
  - 読む前の編集を断ることの評価。
  - 編集した部分を返すかどうかの比較。
  - エージェントの中で `write` に全体を書かせる費用の研究（Aider・FSE の表を除く）。
- 調査の限界：
  - いくつかの論文は PDF を取得できず、arXiv の HTML か要旨から数値を取った（LintEval、LSP、SWE-Touch は要旨のみ）。
  - 調査はサブエージェントが行い、数値は報告からの転記。原文での再確認はしていない。

## 入れなかったもの

- 読んでいないファイルや、読んだ後に変わったファイルの編集を断る確認（Claude Code・DSH にある）。研究の根拠がない。
- 近い行の提示、構文検査：上の候補。採否はユーザーが決める。
- 人に聞くツール、サブエージェント、LSP、ツール検索：以前の比較（`harness-tools.md`）で入れないとした方針のまま。
