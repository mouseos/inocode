# 返答の言語（調査のみ）

- **対象と範囲：** モデルが人に返す文の言語を、inocode がどう決めて指示するか。人が明示した場合と、明示していない場合の両方。
  - 避けたい挙動（ユーザーの報告、2026-11-20）：Muse Code のハーネスは、いちど返答の言語を英語や韓国語に決めると、人が日本語で書き、日本語で話すよう求めても、その言語のまま変わらない。ユーザーの評価は「バグさえ直せば最強」で、言語を固定する考え方そのものではなく、固定が人の指示で変わらないことが問題。仕組みは下の「ほかのハーネス」に記録した。
- **関連コード：** 未実装。いまの inocode のシステムプロンプト（`core/src/turn.rs` の `system_prompt`）には、言語についての指示がない。
- **根拠の状態：** UNSUPPORTED_PENDING。
  - 言語の指示を入れると誤った言語の応答が減ること、指示をプロンプトの途中に埋めると悪いことは、査読ありで確認（下の A1）。ただし 1 ターンだけの実験。
  - 英語の文脈（取得した文書）が英語への切り替わりを招くことは、査読ありで確認（A2）。ただし RAG の実験で、エージェントのツール出力ではない。
  - 長い会話・エージェントの文脈での切り替わり、毎ターンや末尾での指示の繰り返しの効果、最新の発言から言語を判定する方式の評価：研究なし。
- **ユーザーの判断：** 2026-11-20「inocodeに返答文書の言語設定をしないといけない」「ユーザーからの明示がない場合の返答言語…を調べて」。同日、方針として「言語は推定せずOS設定言語使う。指定があったら変える」「設定ファイルからデフォルトをOS規定以外にすることもできるようにしよう。英語設定にしている日本人とかいるし」。実装の承認はまだない。

## 研究（2026-11-20、サブエージェントが原文を読み、数値を報告）

### A1. Marchisio ほか, "Understanding and Mitigating Language Confusion in LLMs", EMNLP 2024（査読あり）

- arXiv 2406.20052、https://aclanthology.org/2024.emnlp-main.380 。15 言語。monolingual（その言語で書き、その言語の返答を期待）2,600 件、cross-lingual（英語で書き、別の言語での返答を指示）4,500 件。
- LPR（誤った言語の行が 1 行もない応答の割合）：GPT-4o は mono 98.9、cross 92.4。GPT-4 Turbo は 99.3、90.3。Llama 3 70B-Instruct は 46.0、30.3。強いモデルでも、英語で書いて別の言語を指示すると約 1 割を誤る。
- 英語中心の調整が混乱を生む例：Llama 2 70B の monolingual LPR（ar/hi/ja/ko/vi/zh 平均）は、基のモデル 98.5、指示調整後 6.0。
- 指示の位置（cross-lingual LPR、先頭／途中／末尾）：Command R 86.7／69.0／85.1、Command R+ 94.4／90.3／95.2、GPT-4 93.0／91.7／95.0。途中に埋めると最も悪く、末尾は先頭と同じかよい。
- 温度が高いほど語の混入が増える（Command R：T=0 で WPR 97.2、T=1.0 で 86.5 か 83.5。本文と表で食い違う）。
- 限界：system メッセージでの指示は調べていない。1 ターンだけで、複数ターンは今後の課題と明記。最大 100 トークンの生成。

### A2. 英語の文脈による切り替わり

- Li・Xu・Xie, "Language Drift in Multilingual RAG", AAAI 2026（arXiv 2511.09984）。中国語の質問に英語の文書を添えると、返答の言語の一貫性が下がる（LLaMA3-8B、HotpotQA：0.981 → 0.883、例示ありで 0.920 → 0.684）。英語が最も強く引き込む。対象言語で答えるよう指示しても、中英の組で 68.4% にとどまった。デコードを変える手法（SCD）で 90.6%。
- 査読前：Zhan ほか（arXiv 2605.27649）は、劣化を最も左右するのは「返答に求める言語」が他と違うこと（一貫性：全部一致 .975、返答の言語だけ違う .860）。BabelArena（arXiv 2609.23490、要旨のみ）は、切り替わりは圧倒的に英語へ向かうと報告。Multi-IF（arXiv 2410.15553）は、ターンが進むほど指示を守らなくなる（言語に限らない）。
- 当てはめ（推測）：コーディング作業の文脈はツール出力・コード・英語の文書で大半が英語なので、指示を先頭に 1 回書くだけでは英語に戻りやすい。

### A3. どの発言から言語を決めるか

- 3 つの方式（最新の発言、最初の発言、固定の設定）を比べた研究は見つからなかった。
- Widdows・Brew（arXiv 2109.09862、査読は未確認）：顧客チャット 5 万会話で、1 つの発言の言語判定が会話全体の判定と違ったのは 12〜14%。「No」のような短い発言は単独では言語が決められない。
- 推測：最新の発言だけで決めると短い発言で誤る。最初の発言で固定すると、Muse Code と同じ固定の問題になる。

## ほかのハーネス（2026-11-20、公開ソース・公式文書で確認）

| ハーネス | 明示の設定 | 設定がないとき | 入れ方 |
|---|---|---|---|
| Claude Code | `language`（公式文書の settings） | 公式文書では既定は未設定 | システムプロンプトに入る（文面は公開されていないため、ここには載せない） |
| Codex CLI | なし | 本体のプロンプトに言語の指示なし（スレッド名などにだけ「ユーザーの言語で」） | — |

| Roo Code | `language` | VS Code の表示言語 | システムプロンプトの独自指示の節 |
| Continue | なし | 指示なし | — |

- Muse Code（Meta、1.4.24-R9131.1、Windows の配布物）：本体の中の文字列を読んだ（静的に読んだだけで、動かして確かめてはいない）。
  - 返答の言語を「固定（pin）」する仕組みがある。固定の値は `english` と `other` の 2 つだけで、`other` がどの言語かは記録しない。固定の出どころは、明示の依頼・十分な長さの文・短い文・既定の 4 種類。固定はセッションの再開でも引き継がれる。
  - モデルへの指示は、`english` なら「英語で書く」、`other` なら「人が決めた英語以外の言語で書く」。どちらも「人がほかの言語で書くか頼むまでは言語を変えない」と付く。
  - 本体には、日本語・韓国語などの言語名を依頼として見分ける語句が見当たらなかった（日本語・韓国語の文字列は、無関係な圧縮用の辞書の中にしかない）。
  - ユーザーの報告する挙動（英語や韓国語に決まると、日本語で頼んでも変わらない）は、次の推測で説明できる。確かめてはいない。
    - 韓国語に固定された後に日本語で書いても、どちらも `other` なので固定は変わらない。モデルには「英語以外の決めた言語を変えるな」とだけ伝わり、それまで使った韓国語を続ける。
    - 英語に固定された後の「日本語で話せ」のような短い依頼は、明示の依頼とも十分な長さの文とも判定されず、固定が変わらない。
  - 当てはめ：言語を固定するなら、どの言語かを名指しで記録し、人の最新の明示を常に優先する。短い発言でも、言語名での依頼は明示として扱う。
- 実務の報告（研究ではない）：oh-my-openagent issue #11527 では、韓国語のユーザーに英語で返し続けた。圧縮の後とツール出力の多いターンで悪化し、要約に「韓国語で返す」と残っていても起きた。提案された直し方は、最新の発言から言語を判定する、圧縮の要約に言語を項目として持たせる、長い英語のツール出力の直後に指示を繰り返す。

## 設計（方針はユーザーの判断。実装は承認待ち）

1. 既定の言語は OS の表示言語（ユーザーの判断）。発言の文から言語を推定しない。Aider が OS のロケールに従うのと同じ考え方（上の表）。
   - 設定ファイルで、既定を OS の表示言語以外にできるようにする（ユーザーの判断、2026-11-20。OS を英語にしている日本語の利用者がいるため）。
2. 人が言語を指定したら、それに変える（ユーザーの判断）。指定は以前の決定より常に優先し、どの言語かを名指しで記録する（Muse Code の問題の回避）。
3. 指示はシステムプロンプトの先頭近くと、会話の末尾（毎回の要求の最後、作業状態を入れている位置）の両方に置く。途中に埋めない（A1）。末尾に置くとキャッシュを崩さない（推測）。
4. 圧縮の要約にも返答の言語を残す（推測。上の実務の報告による）。
- 未解決の論点：OS の表示言語の取り方（Windows・macOS・Linux それぞれ）、「指定」をどう受け取るか（設定と、会話の中の依頼のどちらか、両方か）、指定をセッションの再開で引き継ぐか。
