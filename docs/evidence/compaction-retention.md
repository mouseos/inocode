# 圧縮のあとも、決めたことと確かめた手法を保つ（実験）

- **対象と範囲：** 圧縮の前に決めたこと（作業フォルダー、ポート番号）と、確かめた事実（展開処理の関数名と定数）が、圧縮をはさんでも保たれるかを調べた。いまの圧縮（`agent-tools.md`）と、次の 3 つの追加案を比べた。
  - 確定事項を毎回原文で付ける（`facts` 道具）
  - 要約の前に古いツール出力を消し、決めた見出しで要約する（構造化）
  - 要約を書き直さず、項目を足していく（追記）

  範囲外：キャッシュを崩さない間引き（AgentDiet・TokenPilot 型）、裏でずっと要約しておく方式、部下のエージェントに任せる方式。
- **関連コード：** main には未実装。実験用の切り替えは手元のブランチ `exp/context` にだけある：
  - `INOCODE_EXP_FACTS`：`facts` 道具と、毎回の要求に付ける一覧。
  - `INOCODE_EXP_COMPACT=structured|append`。
  - `INOCODE_EXP_WINDOW`：窓の大きさの上書き。
  - 実験の台本：`refs/ctx-bench/`（git の対象外）の `run_ctx.py`、`score_ctx.py`、`stats.py`。
- **根拠の状態：** UNSUPPORTED_PENDING。
  - 研究では、確定事項を毎回付けることと、構造化の要約が支持されている（下記）。
  - しかし、このプロジェクトの実測では、いまの圧縮に足しても良くならず、費用が増えた。main には入れていない。
- **ユーザーの承認：** 2026-11-20「有用な手法をリストアップして。圧縮と記憶に関して深夜中に対照実験を回す」。対照実験までの承認。

## 学術資料（調査結果の要点）

- Chen, "Governance Decay"（査読前）。[arXiv 2606.22528](https://arxiv.org/abs/2606.22528)
  - 圧縮のあと、規則の違反は 30%。規則を約 47 トークンで毎回付けると、7 モデルすべてで 0% に戻った。
- Satish ほか, "Beyond Token Savings"（査読前）。[arXiv 2609.32961](https://arxiv.org/abs/2609.32961)
  - 古いツール出力を消してから決めた見出しで要約すると、SWE-bench で +7.7〜9.7 点。
- Zhang ほか, "Agentic Context Engineering", ICLR 2026（査読済み）。[arXiv 2510.04618](https://arxiv.org/abs/2510.04618)
  - 文脈全体を書き直し続けると崩れた。項目ごとに足す方式では崩れなかった。
- Yang ほか, "SWE-agent", NeurIPS 2024（査読済み）。
  - 古い出力を 1 行にまとめた方が、全部残すより解けた（18.0% 対 15.0%）。
- どれも、このプロジェクトのいまの圧縮を比較の基準にしていない。いまの圧縮は、人の発言を原文で残し、呼び出しの記録はハーネスが機械的に作り、直近は原文で残す。比べた相手は、全文を要約する方式などだった。

## このプロジェクトの実測（2026-11-20）

### 方法

- **課題：** 合成のファームウェア展開（`method-memory.md` と同じ形式）を、1 つのスレッドで 7 ターン続ける。
  - ターン 1：手順を調べて区画 0 を開く。作業フォルダーと、後で使うポート番号を自分で決めさせる。
  - ターン 2〜6：区画 1〜5 を開く。毎回、先頭 60 行を答えに引用させる（文脈を増やすため）。ERROR の行数と、一番多いエラーコードを答えさせる。
  - ターン 7：区画 6 を作業フォルダーに保存し、`server.cfg` に最初に決めたポートを書く。展開処理の関数名（FUN_00402210）と、区画の番号に掛ける定数（0x5A）を答えさせる。
- **窓：** 24,000 トークンに上書きした（80% で圧縮）。1 回の実行で、圧縮は 4〜12 回起きた。
- **比べた方式：**
  - `base`：いまの圧縮
  - `facts`：＋確定事項
  - `structured`：＋古い出力を消す＋決めた見出しの要約
  - `fs`：facts＋structured
  - `full`：facts＋追記。1 回で打ち切り（下記）
- **モデル：** Claude `claude-haiku-5-5`、Meta `muse-spark-1.3-contributor`。繰り返しは各 8 回。繰り返し r は同じ課題の変種を使う。対応のある並べ替え検定（両側）。
- **除外：** Haiku の facts の 8 回目と fs の 4 回目は、実験の家フォルダーを誤って消し、認証の読み込みが 1 回失敗した。この 2 回は捨てて、流し直した（捨てた結果は `refs/ctx-bench/main/excluded/`）。

### 分かったこと（実測の範囲での判断）

1. いまの圧縮で、決めたこと（フォルダー・ポート）は、両モデルとも 8/8 保たれた。この課題では、「圧縮のあとに決めたことを忘れる」は起きなかった。
   - いまの圧縮は、人の発言・機械的に作る呼び出しの記録・直近の原文を残す。研究で比べられた「全文を要約する方式」とは、条件が違う。
2. 確定事項を毎回付けると、Haiku で新しい失敗が出た。圧縮のあと、いまの質問ではなく、ターン 1 の答え（フォルダー・型番・ポート）をもう一度答えてしまう。ターン 2〜6 の正答率は 1.00 から 0.73 に下がった（facts と fs の両方、p=0.031）。毎回付けた一覧に引っぱられて、いまの作業を見失ったとみられる。Muse では起きなかった。
3. 古い出力を消してから要約すると、loader を読み直す回数と費用が増えた。
   - 例：Haiku の structured の 1 回目は、ターン 7 で loader を 43 回読んだ。
   - 要約する側が出力を見られず、関数名などの事実が要約に残らなかったとみられる（推測）。
   - 研究の結果（+7.7〜9.7 点）は、この条件では再現しなかった。
4. 追記（要約を書き直さず足していく）は、上限がないと要約がふくらみ続けた（1 回の実行で約 45,000 字）。毎回の要求が窓の 80% を超えて、圧縮が止まらなくなった（`full`：1 回の実行で圧縮 66 回、入力 781 万トークン）。そこで打ち切った。採るなら、要約の大きさの上限か、まとめ直しが要る。
5. 両モデルとも、追加案はどれも保ち方を良くせず、費用を増やした。いまの圧縮のままにする。

### 限界

- 合成の課題 1 種類。決めたことは 2 つ（フォルダー・ポート）だけ。人の発言に答えのヒント（「最初に決めたポート」）があり、要約や記録に残りやすい形だった。
- 窓を人工的に小さくした（24,000）。実際のモデルの窓ではない。
- ユーザーの困りごと（圧縮のあとにログの書き出し先を変える、確かめた手法を使わず一般論に戻る）は、このハーネスと課題では再現しなかった。ほかのハーネスや、もっと長い実作業で起きる可能性は残る。
- 繰り返しは 8 回で、正答の差は小さい。
