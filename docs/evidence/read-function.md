# read で定義を名前で読む

- **対象と範囲：** `read` に定義の名前を渡すと、その関数・型などの範囲だけを返す。範囲が窓（100 行）より長いときは、定義の中を窓で区切って返し、続きの読み方を示す。範囲の終わりを決める方法と、その正確さの実測を含む。編集は範囲外。
- **関連コード：** `core/src/read.rs`（`read`）、`core/src/outline.rs`（定義の取り出し）。
- **根拠の状態：** RESEARCH_SUPPORTED（CODESTRUCT。Python のみ）。範囲の終わりを言語によらず決める規則と、大きな定義を窓で区切る扱いは、研究がない工学上の選択。

## 学術資料

- Kim et al., "CodeStruct: Code Agents over Structured Action Spaces", arXiv 2604.05407v3（arXiv の注記では ACL 2026 採択）。https://arxiv.org/html/2604.05407
  - readCode：ファイルのパスと、任意の名前（`User.load` のような修飾名も可）を受け取り、名前が合う各要素の実装を丸ごと返す。名前がなく、ファイルが閾値（例：1 万文字）より大きいときは、トップレベルの要素のシグネチャを返す。要素の位置は tree-sitter で決める。
  - SWE-bench Verified、Table 1（Pass@1 %、費用 $。比較対象は SWE-agent と OpenHands で、SWE-agent のリポジトリ地図あり）：

| モデル | 比較対象 | CodeStruct |
|---|---|---|
| GPT-5 | 66.0 / 574.0 | 67.2 / 462.2 |
| GPT-5-mini | 60.4 / 151.0 | 62.0 / 101.8 |
| GPT-5-nano | 19.6 / 40.7 | 40.4 / 57.3 |
| Qwen3-Coder | 61.2 / 365.3 | 66.2 / 321.3 |
| Qwen3-32B | 14.8 / 55.6 | 16.0 / 45.9 |
| Qwen3-8B | 13.2 / 2.36 | 13.0 / 1.46 |

  - readCode だけを外した分解実験（Table 4。2 モデルのみ）：Qwen3-32B 16.0・$45.93 → 8.2・$64.58。GPT-5-mini 62.0・$101.83 → 56.8・$109.46。
  - 費用が下がる理由として、論文は大きなファイルの読み込みが減り、必要な要素だけを読むことを挙げる。
  - 限界：
    - 評価は Python（SWE-bench）。CodeAssistBench は 7 言語だが、Qwen3-32B では入力トークン +28.9%、費用 +23.7%。
    - GPT-5-nano は費用 +40.8%。
    - 繰り返し実行やばらつきの報告はない。
    - 巨大な関数やクラスの扱い（上限、切り詰め、分割）は書かれていない。
    - 名前が見つからないときの扱いは readCode について書かれていない。複数一致はすべて返す。

## 設計（研究がない工学上の選択）

- 名前の一致：`find` の名前検索と同じ定義の取り出し（`core/src/outline.rs`）を使い、名前の完全一致で探す。
- 同じ名前が複数あるとき：`from` の行を含む定義、なければ最初の定義を返し、ほかの定義の行を示す。
- 大きな定義：窓は既存の `read` と同じ 100 行（SWE-agent の窓。`harness-tools.md`）。定義が長ければ、その中の 100 行を返し、続きの `from` を示す。
- 範囲の終わり：
  1. tree-sitter の言語（Rust・Python・JS・TS・TSX・Go・Java・C・C++）：構文木の定義の範囲。
  2. それ以外：字下げの規則。定義の行より字下げが深い行が続く間を本体とし、その後の最初の同じか浅い字下げの行が閉じ（`}`・`end` など）ならそれも含める。本体の行がないとき（Markdown の見出しなど）は、同じか浅い字下げの次の定義の手前まで。
     - ただし、その深さの行でも、`{` だけの行と、シグネチャを閉じて本体を開く行（`) -> T {`、`):`）では終わらない。
  - C と C++ の tree-sitter の tags は、関数の宣言子（名前と引数）だけを定義の範囲にする。そのため構文木をたどり、囲んでいる `function_definition` の終わりを使う。
  - ハイライト用の文法の印で本体の範囲を取る方法（承認時の案の 2 段目）は作っていない。字下げの規則の正確さ（下）で足りると判断した。足りない言語が見つかれば検討する。

## 字下げの規則の正確さ（プロジェクト内の実測、2026-11-18）

- 方法：tree-sitter がある言語のファイルで、字下げの規則で決めた終わりの行を、構文木の終わりの行と比べた。複数行の定義だけを数えた。ファイルは `outline` の比較と同じ一覧（`refs/outline-bench/lists`、git 管理外）。測定は `core/src/outline.rs` の無効化したテスト `indentation_ends_against_tree_sitter`。
- 結果（構文木を正解とした割合）：

| 言語 | 定義の数 | 一致 | 短すぎる | 長すぎる（平均の超過行数） |
|---|---|---|---|---|
| Rust | 41,125 | 0.961 | 0.032 | 0.006（14.7 行） |
| Python | 4,999 | 0.988 | 0.012 | 0.001（2.0 行） |
| Go | 4,308 | 0.984 | 0.016 | 0.001（4.3 行） |
| C | 6,881 | 0.960 | 0.019 | 0.021（4.4 行） |
| TypeScript | 57 | 1.000 | 0 | 0 |

- 測る過程で直したこと：
  - 最初の規則では、Rust の一致は 0.795 だった。複数行のシグネチャの `) -> T {` で止まっていたのが原因で、上の例外を加えた。
  - C の tags の範囲が宣言子だけだったため、最初は構文木の「正解」そのものが誤っていた。
- 限界：
  - 正解として使ったのは、tree-sitter がある言語だけ。規則が実際に使われるのは tree-sitter のない言語なので、そちらでの正確さは、この数字からの推測でしかない。
  - コードの書き方（字下げの習慣）が違うリポジトリでは、結果が変わりうる。
  - 各言語 1 回の測定。

## ユーザーの承認

- 2026-11-18：名前で丸ごと読む案、大きな関数は関数の中を窓で区切る扱い、終わりの決め方を段階に分ける案を承認（「いいよ」）。

## 実装・検証の状況

- 実装済み：`read` の引数 `name`。
- テスト（`core/src/read.rs`）：
  - 長い定義を窓で区切り、続きの `from` を示す。
  - 同じ名前の定義を `from` で選ぶ。
  - C の関数が本体まで含まれる。
  - 字下げの規則で Ruby のメソッドと Markdown の見出しの範囲を決める。
- エージェントの正確さとトークンへの効果は未検証。巨大なリポジトリでの対照実験を予定。
