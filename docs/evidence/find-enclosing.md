# 検索結果に、その行を含む定義の名前を付ける

- **対象と範囲：** `find` の内容検索で、表示する一致（最大 50 件）それぞれに、その行を含むいちばん内側の定義（関数・メソッド・型・見出し）の名前を `path:line (in name): text` の形で付ける。定義の範囲は `read` の名前読みと同じ取り出し（`core/src/outline.rs`。tree-sitter、なければ字下げの規則）。定義の分からない言語のファイルは名前を付けない。範囲外：名前検索とファイル名検索、50 件を超えた一致。
- **関連コード：** `core/src/find.rs`（`name_enclosing`）、`core/src/outline.rs`。
- **根拠の状態：** UNSUPPORTED_APPROVED（研究のない独自の方法。対照実験を条件に承認）。

## なぜこの方法か（プロジェクト内の実測からの推測）

- `read` の名前読みのカーネル実測（`read-function.md`、難しい課題）で、2 段の呼び出し元の課題 30 ターン分のツール出力を数えた：
  - 名前読みのない版：`read` 41 万文字、`find` 26 万文字。
  - 名前読みのある版：`read` 21 万文字、`find` 57 万文字。
- 推測：
  - どちらの版も、検索で見つけた行がどの関数の中にあるかを調べるために、トークンを使っていた。
  - 名前のない版は、ヒットした行の周りを読んで確かめていた。
  - 名前のある版は、読む前に名前を知る必要があるため、検索を増やしていた。
  - 一致した行に関数名が付いていれば、どちらも要らなくなる。
- これは記録を数えた結果からの推測で、効果は確かめていない。

## 効果の実測：Linux カーネル

- 条件：`read-function.md` の難しい課題と同じ 40 課題（2 段の呼び出し元 15、呼び出し先 15、要約 10）、Claude Haiku 5.5、Claude OAuth、各 2 回、使い方の指示あり、2026-11-18。
  - C：キャッシュ＋名前付け（「2＋1」）。D：キャッシュ＋名前付け＋古い出力を隠す（「2＋1＋3」）。C と D は同じ時間帯に 1 ターンずつ交互に実行した。
  - 比較の A（名前読みあり・指示あり）と B（名前読みなし）は、同じ課題の以前の実行（`read-function.md`）。**同時の対照ではない**。モデル側の変化が混ざりうる。
  - 160 ターンすべて完了。要求の失敗はなかった。
- 結果（中央値。入力はキャッシュから読んだ分を含む総数。「キャッシュ外」は入力からキャッシュ読み込みを引いた数）：

| 2 段の呼び出し元 | A | 0.972 | 76,530 | 76,530 | 8 | 48 |
| | B | 0.972 | 76,057 | 76,057 | 8 | 43 |
| | C | 0.972 | 14,740 | 3,080 | 4 | 21 |

- 検定（課題ごとに 2 回を平均、Wilcoxon 符号順位、40 組）：
  - C と A：正答に差なし（p=0.92）。入力総数は C が少ない（差の中央値 5,703、p=0.004）。要求数・時間も C が少ない（p=0.003）。
  - 2 段の呼び出し元だけでは、入力総数の差の中央値 49,675（p<0.001）、要求数 4.5（p=0.001）、時間 30 秒（p<0.001）。
  - 呼び出し先では入力総数に差なし（p=0.52）。
- 読み取り：
  - キャッシュは入力総数を変えない。入力総数の減少は名前付けによると考えられる。ただし A・B は同時の対照ではないため、確定ではない（推測）。
  - 減ったのは 2 段の呼び出し元に集中した。検索結果に関数名が付けば、呼び出し元の関数を読んで確かめる手間が要らない課題である。
  - 正答率は変わらなかった（どの版も上限に近い）。
  - 呼び出し先の正答 0.92〜0.93 は、正解の欠陥（`read-function.md`）で低く出ている。欠陥を除いた再現率は C 0.993、D 0.983。
