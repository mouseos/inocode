# TCP フレームプロトコル（JSON + 生バイナリ）

## 対象と範囲

- 対象: `inocode` ライブラリの TCP フレーミング。1 本の TCP 接続で JSON 制御メッセージ（Type=1）と生バイナリ（Type=2）、転送終了（Type=3）を送受信する。
- 範囲外: LLM 接続、エージェント、セッション管理、会話履歴、SQLite、RAG、ツール実行、承認、GUI、製品用 CLI。実装していない。
- プロトコル仕様（16 バイトヘッダー、ビッグエンディアン、Type 1/2/3、Stream ID、Flags/Reserved は 0 固定）はユーザー指示で確定済みであり、本実装はその仕様の実装のみを行う。

## 関連ソースコード

- `src/frame.rs` — ヘッダーのエンコード/デコードと検証、上限値、チャンクサイズ。
- `src/stream.rs` — `FrameReader` / `FrameWriter`（JSON・バイナリ送受信、Stream ID 識別、分割送受信、切断処理）。
- `src/error.rs` — `ProtocolError`。
- `src/lib.rs` — 公開 API の再エクスポート。
- `tests/tcp_protocol.rs` — 実 TCP 接続による統合テスト（14 件）。
- `tests/measure.rs` — リリースビルドの計測（`#[ignore]`、明示実行）。
- `tests/common/mod.rs` — テスト用の TCP ハーネス（本番と同じ `FrameReader`/`FrameWriter` を使用）。

## 根拠の状態

- **UNSUPPORTED_APPROVED** — プロトコル仕様・通信方式・依存ライブラリ（Tokio、serde/serde_json）はユーザー指示で確定しており、有効性を学術研究で主張しない。承認内容の参照元は本タスクの実装指示（フレーム仕様、§5「既存の Tokio などのライブラリを活用」）。
- 設計判断（`DEFAULT_MAX_PAYLOAD_LEN = 16 MiB`、`CHUNK_SIZE = 64 KiB`）は研究根拠ではなく、**実測（下記）とメモリ安全性**に基づく。最適値であるとは主張しない。
  - 16 MiB 上限: ピアが 1 フレームで要求できるメモリを有界にするため。大容量はフレーム分割で送る前提であり、上限を上げる必要がない。
  - 64 KiB チャンク: Windows 実機の実測で高速側の帯域に入り（中央値 約 3.2 GiB/s）、1 フレームあたりのバッファを 64 KiB に抑えられるため。8 KiB はフレーム数増加により Windows で明確に遅かった（中央値 約 0.87 GiB/s）。1 MiB も高速だったが、フレーム単位のメモリが増えるため既定値には採らない。Linux / macOS の実測値はない（CI はテストのみで計測しない）。
- 1 フレームは「ヘッダー + ペイロード」を 1 回の vectored write で書き出す。ヘッダーとペイロードを別々に書くと、小さなヘッダーが Nagle で保留されやすいため。計測ノイズが大きく、この変更単独の効果は数値で断定しない。

## 検証済みの主張

- `cargo test`（Windows 11）で単体 17 件 + TCP 統合 14 件が成功。debug と release の両方で実行。
- `FrameWriter::write_json` はカウント付きライターで直列化するため、上限を超える JSON ペイロードは上限分を超えてバッファリングされることなく `PayloadTooLarge` で拒否される。上限ちょうどの値は送信できる。`FrameReader` 側の上限検査は変更なしで維持。
- `cargo clippy --all-targets` 警告なし、`cargo fmt --check` 差分なし、`cargo doc --no-deps` 警告なし。
- 統合テストは実際の `TcpListener`/`TcpStream`（ループバック）で、本番と同じライブラリのみを使用する。

## 学術的な主張・不足点

調査方法: `web_search` による検索（2026-11-15）。**適用可能な学術研究は確認できなかった。**

- フレーミング方式（長さ前置 vs 区切り文字）の優劣を評価した学術研究は見つからなかった。確認できたのは実務解説と公式仕様のみであり、研究根拠としては扱わない。
- 16 バイトヘッダーという固定長、Type/Flags/Reserved の配置、Stream ID の幅、ペイロード上限 16 MiB、チャンク 64 KiB のいずれについても、直接適用できる研究は未確認。判断根拠は凍結された仕様（ユーザー指示）と実測、およびメモリ安全性の要請である。
- 1 フレーム 1 回の vectored write による Nagle 遅延の回避は、TCP の挙動に関する一般的な説明に基づく設計判断であり、効果を測定で断定していない。
- 不足: 不正フレームの拒否（Flags/Reserved 非ゼロ、未知 Type、長さ不整合）が攻撃耐性をどれだけ高めるかを評価した研究は確認していない。実装は仕様適合とテストによる確認に留まる。
- `write_json` の送信上限は無制限メモリ確保を防ぐための境界であり、輸送層のペイロード上限と同じ値を用いる。境界値の妥当性を評価した研究は未確認。

## その他の根拠（研究とは区別する）

- ユーザー指示による凍結仕様: 16 バイトの固定ヘッダー、ビッグエンディアン、Type 1/2/3、Stream ID、Flags/Reserved は 0 固定、JSON と生バイナリの同一接続混在、Base64 不使用。
- 公式仕様: HTTP/1.1（RFC 9112）のメッセージフレーミングや HTTP/2（RFC 9113）の多重化など、長さ前置とストリーム識別は広く使われている方式である。ただしこれは方式の一般性を示すもので、本実装の有効性評価ではない。
- 実測（本リポジトリ）: 下記「測定」の Windows 実機値、および統合テスト 14 件の結果。仕様適合と動作の確認であり、学術的有効性の証明ではない。

## 測定

環境と方法（数値はすべて実測。推測値なし）:

- リリースビルド（`cargo test --release --test measure -- --ignored --nocapture --test-threads=1`）。
- クライアントとサーバーを同一プロセス内で動かし、`127.0.0.1` の TCP で接続。Tokio マルチスレッドランタイム（ワーカー 2）。
- Windows: Microsoft Windows 11 Home build 26200、AMD Ryzen AI 9 HX 370（12 コア/24 スレッド）、24 GiB RAM、rustc 1.93.1。Spotify/Discord など常駐アプリが動作中で、実行ごとのばらつきが大きい。
- メモリはプロセスの peak working set（`(Get-Process).PeakWorkingSet64`）、CPU はプロセス CPU 時間（`(Get-Process).CPU`）を計測。いずれもクライアント+サーバー合算。
- Linux 実機での測定は未実施（下記「未検証の主張」）。
- 転送速度は 512 MiB を 5 回送り、中央値と最良/最悪を記録（受信側は破棄カウントのみでハッシュ計算を除外）。

小さな JSON 往復（ペイロード 71 バイト、2000 サンプル、ウォームアップ 200 回）:

| | Windows 11 |
|---|---|
| 平均 | 27.50 µs |
| 最小 | 19.50 µs |
| p50 / p95 / p99 | 24.50 / 45.30 / 79.70 µs |
| 最大 | 235.70 µs |
| 往復/秒 | 36,278 |

大容量バイナリ転送（512 MiB、5 回の中央値）:

| チャンク | Windows 11 |
|---|---|
| 8 KiB | 867.9 MiB/s（最良 1770.6 / 最悪 569.9） |
| 64 KiB | 3186.9 MiB/s（最良 4088.9 / 最悪 2003.3） |
| 256 KiB | 1043.4 MiB/s（最良 2013.2 / 最悪 779.0） |
| 1 MiB | 4086.9 MiB/s（最良 4920.1 / 最悪 1911.8） |

メモリと CPU:

| | Windows 11 |
|---|---|
| 転送前の peak working set | 7.7 MiB |
| 4 MiB 転送後 | 7.7 MiB |
| 512 MiB 転送後（64 KiB フレーム） | 7.7 MiB |
| 512 MiB 転送の CPU 時間 | 0.188 s（壁時計 0.234 s、1 コアの 80.3 %） |

解釈の範囲: ペイロードを 4 MiB から 512 MiB に増やしても peak working set が増えないことから、送受信ともストリーミングで全データを保持していないことを確認した。転送速度は同一マシン上でも実行間のばらつきが大きく、上表の値は環境依存の参考値であって上限性能ではない。
- 再実行によるばらつきの記録: 同一環境・同条件下で 2026-11-15 に再実行したところ、小さな JSON 往復の平均は 63.16 µs（min 22.60 µs、p50 46.90 µs、p99 225.70 µs）、大容量転送の中央値は 8 KiB 1563.5 / 64 KiB 2306.7 / 256 KiB 985.5 / 1 MiB 905.6 MiB/s であった。64 KiB が最速クラスという結論は再現したが、絶対値は初回測定（27.50 µs、64 KiB 3186.9 MiB/s）と大きく異なり、常駐プロセスの負荷などの環境要因に強く依存する。いずれの値も最適値の断定には使えない。
