# 確かめた手法を記憶して、別のプロジェクトで使い回す

- **対象と範囲：** モデルが確かめた手法（実際の手順、効かなかった方法、対象の識別子、見つけたプロジェクト）をメモとして保存し、似た課題で使い回すこと。保存の道具、作業の始めに見せる方法、`recall` で引く方法を比べた。範囲外：タグの選ばせ方（既存から選ぶ／作る）、識別子での文字一致の検索、メモの古さの管理。
- **関連コード（main）：**
  - `core/src/agent_tools.rs` の `method` 道具。識別子・題名・手順は必須で、効かなかった方法とタグは任意。見つけたプロジェクトのフォルダーは、ハーネスが本文に入れる。共有（プロジェクトなし）の手順メモとして保存し、すぐ使える状態にする。
  - 作業の始めに見せる仕組みは、既存の `render_lessons`（`lessons_for`）をそのまま使う。手順メモも 1 行で出る。
  - `recall` は、手順メモに当たると本文を全文返す。
  - `core/src/turn.rs` のシステムプロンプトに、`method` で保存し、調べ始める前に `recall` で探す、の 2 文を足した（実験の `recall`／`pull` 方式と同じ文）。
  - テスト：`server/tests/turn_tcp.rs` の `methods_are_shared_across_projects_and_recalled_whole`。
- **実験時のコード：** 切り替えは手元のブランチ `exp/context` にだけある（push していない）：
  - `core/src/agent_tools.rs` の `method` 道具。識別子と手順は必須。保存先は共有で、見つけたプロジェクトは本文に入れる。
  - `INOCODE_EXP_MEMORY`：`recall`／`auto`／`pull` の 3 方式。
  - `recall` に、保存した手法の本文を全文表示する変更（`pull` のとき）。
  - 実験の台本：`refs/ctx-bench/`（git の対象外）の `gen_fw.py`、`run_mem.py`、`score_mem.py`、`stats.py`。
- **根拠の状態：** 部分ごと。
  - 手法を保存して使い回すこと自体：RESEARCH_SUPPORTED（下の AWM）。加えて、このプロジェクトの実測でも効果があった。
  - 識別子を必須にすること、ハーネスが作業の始めに見せること、「一般知識より優先」と書くこと：UNSUPPORTED_PENDING（研究なし。実測は下記。main への実装は承認済み、UNSUPPORTED_APPROVED）。

## 学術資料

- Wang, Mao, Fried, Neubig, "Agent Workflow Memory", ICML 2025（PMLR 267、査読済み）。[arXiv 2409.07429](https://arxiv.org/abs/2409.07429)
  - 過去の実行から作業の流れを取り出し、後の課題で使う。成功率は、Mind2Web で相対 +24.6%、WebArena で相対 +51.1% 上がった。
  - 課題・サイト・分野をまたいだ使い回しでも、比較対象を 8.9〜14.0 点上回った。
  - Web の課題だけで試している。
- Ouyang ほか, "ReasoningBank", ICLR 2026（arXiv のコメントによる）。[arXiv 2509.25140](https://arxiv.org/abs/2509.25140)
  - 失敗した実行からも戦略を取り出すと良くなった。要約に数値はない。
- Xiong ほか, "How Memory Management Impacts LLM Agents"（査読前）。[arXiv 2505.16067](https://arxiv.org/abs/2505.16067)
  - 間違った記憶は、後の課題に誤りを広げる。
  - 厳しい確認を通ったものだけ保存すると、何でも保存するより良かった（EHRAgent：13.05 → 38.50）。
- Wu, Wu, Zou, "ClashEval", NeurIPS 2024 Datasets and Benchmarks（査読済み）。[arXiv 2404.10198](https://arxiv.org/abs/2404.10198)
  - モデルは、自分の答えが正しくても、間違った文脈に 60% 以上の割合で従った。記録を強く信じさせる指示には、間違った記録にも従う危険がある。
- 自動で見せる方式と、モデルが引く方式を直接比べた研究は見つからなかった。リバースエンジニアリングや端末の改造での記憶の研究も見つからなかった。

## このプロジェクトの実測（2026-11-20）

### 方法

- **課題：** 合成のファームウェア展開（`gen_fw.py`）。
  - `fw.bin` の各区画は、zlib の頭がない raw deflate を、区画の番号と種から作った鍵で XOR したもの。一般的な道具（zlib・binwalk）では開けない。
  - 正しい手順は、逆コンパイル風の `loader_decomp.c`（約 1,550 行の中に、本物の処理が 2 つ埋もれている）を読めば分かる。
- **流れ：** 1 回の実行は、同じサーバーで 2 つのスレッドを順に流す。
  - プロジェクト 1：BX-7 の区画 0 を開く。
  - プロジェクト 2：別フォルダーの BX-9（同じ方式、別の種）。区画 3 を開き、SHA-256 を答える。
  - BX-9 の README には「区画は普通の zlib で、zlib.decompress で開ける」という誤った注記を入れた。
  - 繰り返しは 8 回。繰り返しごとに家のフォルダーを作り直すので、前の回の記憶は持ち越さない。
  - 繰り返し r は、どの方式でも同じ課題の変種を使う（対応のある比較）。
- **比べた方式：**
  - `none`：記憶の道具なし。
  - `recall`：`method` 道具あり。保存した手法は、既存の教訓の仕組み（`lessons_for` が手順のメモも返す）で、作業の始めに 1 行にまとめて見せる。
  - `auto`：`recall` に加えて、手法の全文を「一般知識より優先」という見出しつきで、もう一度見せる。
  - `pull`：作業の始めには見せない。モデルが `recall` で引く。返るのは検索の抜粋だけ。
  - `pull2`：`pull` と同じだが、`recall` が手法の全文を返す。
- **モデル：**
  - Claude `claude-haiku-5-5`（Claude OAuth）。
  - Meta `muse-spark-1.3-contributor`（Muse Code のサブスクリプション。この実験の途中で直した、組み込みツール名の言い換えを使った）。
- **検定：** 同じ課題の変種どうしの差を取り、符号を入れ替える並べ替え検定（両側、正確）。8 組では、p の最小値は 0.0078。

### 結果（プロジェクト 2 の平均。8 回）

正答はすべての方式で 8/8 だった（課題が易しく、差は出ない）。差は費用と時間に出た。

**Claude Haiku**

| 方式 | 入力トークン | ツール呼び出し | 秒 | loader を読んだ回数 |
|---|---|---|---|---|
| none | 311,261 | 23.4 | 101.6 | 7.1 |
| recall（始めに 1 行で見せる） | 49,164（−84%、p=0.008） | 8.3（p=0.008） | 45.6（p=0.008） | 0.4（p=0.008） |
| auto（全文も見せる） | 103,066（−67%、p=0.008） | 13.4（p=0.008） | 71.0（p=0.023） | 3.5（p=0.094） |
| pull（抜粋だけ、n=5） | 301,207（p=0.81） | 27.4（p=0.50） | 101.2（p=1.0） | 6.0 |
| pull2（全文を引ける） | 123,960（−60%、p=0.008） | 13.9（p=0.008） | 55.5（p=0.016） | 3.5（p=0.062） |

**Muse Spark 1.3 contributor**

| 方式 | 入力トークン | ツール呼び出し | 秒 | loader を読んだ回数 |
|---|---|---|---|---|
| none | 521,449 | 32.1 | 156.5 | 10.3 |
| recall（始めに 1 行で見せる） | 102,174（−80%、p=0.008） | 14.3（p=0.008） | 52.8（p=0.008） | 2.8（p=0.008） |
| pull（抜粋だけ） | 593,625（p=0.60） | 36.0（p=0.41） | 161.1（p=0.84） | 10.1 |
| pull2（全文を引ける） | 137,193（−74%、p=0.008） | 15.3（p=0.008） | 78.0（p=0.008） | 4.3（p=0.031） |

- 方式どうしの比較（Haiku）：`recall` は `auto` より入力が少なかった（差 53,903、p=0.023）。`pull2` よりも少なかった（差 74,797、p=0.008）。
- 方式どうしの比較（Muse）：`recall` は `pull2` より速かった（差 25.3 秒、p=0.023）。入力の差は有意でない（p=0.10）。
- プロジェクト 1 で、`method` 道具があるときは、どの方式でも 8/8 の実行で手法を保存した。保存させる 1 文をシステムプロンプトに入れた結果で、道具の説明だけのとき（試しの実行、1 回）は保存しなかった。

### 分かったこと（実測の範囲での判断）

1. 確かめた手法をメモにして、似た課題の始めに見せると、2 つのモデルとも、調べ直しが大きく減った。入力は −80〜84%、時間は −55〜66% だった。
2. 見せ方は、短い 1 行で十分だった。「一般知識より優先」の見出しで全文をもう一度見せても、良くならなかった（Haiku では、かえって入力が増えた）。
3. モデルが自分で `recall` で引く方式でも効く。ただし、`recall` が手法の本文まで返す場合に限る。いまの `recall` はメモの抜粋（題名ほど）しか返さず、その場合は記憶なしと差がなかった（両モデル）。
4. 誤った注記（zlib で開ける）への飛びつきは、Muse ではどの方式でも約 1 回あった（記憶ありでも減らなかった）。Haiku ではほとんどなかった。

### 限界

- 合成の課題 1 種類だけ。課題が易しく、正答には差が出なかった。費用と時間の差だけを示す。
- 手法を保存した実行と、それを使った実行は、同じ方式の内側で続けて流した。保存の失敗や、間違った手法が保存された場合の害は、試していない。
- 識別子の必須、タグの統制、文字一致の検索の効果は、この実験では切り分けていない。
- モデルは 2 つ、繰り返しは 8 回。

## 実装した項目（2026-11-20 承認）

- `method` 道具（識別子と手順を必須にし、効かなかった方法も書く。見つけたプロジェクトはハーネスが入れる。共有で保存する）。
- 保存した手法を、作業の始めに短く見せる。既存の教訓の仕組みは、すでに手順のメモも返す。
- `recall` で、手順のメモは本文まで返す。
