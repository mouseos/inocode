# 使用量のログと、モデルごとの速さ

- **対象と範囲：** モデルへの要求を 1 件ずつ記録し、モデルごとに、トークン、キャッシュから読んだ割合、最初の文字までの時間、出力の速さ（tok/s）を、時間帯ごとにも返す。後でモデルの割り振り（速いモデルに任せる、時間帯で選ぶ）に使えるようにする。
  - 範囲外（未実装）：費用の計算（価格は `models/catalog` にあるが、記録と掛け合わせていない）、ストリームを始める前に失敗した要求の記録、古い記録の削除、記録をもとにした自動の割り振り。
- **関連コード：** `core/src/usage_log.rs`（記録、集計）、`core/src/llm.rs`（`RequestRecord`、`ChatStream::record`、`Llm::provider_label`）、`core/src/turn.rs`（`TurnUsage::add_stream`、ターンの終わりの書き込み）、`core/src/store.rs`（スキーマ v6 の表 `requests`）、`core/src/lib.rs`（`Request::stats_window`、`Core::model_stats`）、`server/src/lib.rs`（`stats/models`）。
- **根拠の状態：** UNSUPPORTED_APPROVED。記録と表示の機能で、効果の研究はない。
- **ユーザーの判断：** 2026-11-21「使用量ログもほしい。これはopencodex実装が参考になる」「dshのようにキャッシュとかtok/sとかデータも取得して。そしてモデルごとに記憶して。早いやつに仕事割り振るとか後にできる。8時はこいつが早くて頭いいので任せようとかできる」「寝るので自動でできることすべて実装」。

## 参考にした実装（2026-11-21、サブエージェントがソースを読み、報告）

- opencodex（`refs/opencodex` の `src/usage/*`）：要求ごとに 1 行の JSONL（`usage.jsonl`、追記だけ）を書き、そこから作り直せる SQLite の索引を持つ。項目は時刻、提供元、モデル、トークン（入力、出力、キャッシュの読み書き、推論）、全体の時間、最初の出力までの時間など。費用は保存せず、読むときに価格表から計算する。既定では消さない（上限を設定すると古い行を削る）。
- 旧版の inocode（`ino-code` の `ext/inocode-stats`）：`stats/requests.jsonl` に、時刻、出どころ、スレッド、モデル、提供元、トークン、生成の時間、tok/s を記録。実測の価格と速さを読むときに計算する。

## 実装

- 記録の作り方：`Llm::converse` が要求を送る前の時刻を `ChatStream` に持たせ、ストリームが最初の文字を返した時刻も持つ。`TurnUsage::add_stream` が、トークンを足すのといっしょに `ChatStream::record` の記録を集める。対象はターンの要求（`turn`）、探索役（`explore`）、同僚（`colleague`）、圧縮の要約（`compact`）、審査役（`review`。DeepAI の審査の仕組みは除く）。
- 書き込み：ターンの終わりに、そのターンの記録をまとめて 1 回の書き込み（1 つのトランザクション）で表 `requests` に入れる。流れてくる文字ごとには書かない（Codex の SSD への書き込みの問題を避ける。`harness-tools.md` の点検）。書き込みに失敗しても、ターンは失敗にせず標準エラーに出す。
- 項目：送った時刻（ミリ秒）、スレッド、用途、提供元（サインインの提供元はその名前、鍵の提供元は API の形式とホスト。例 `openai@api.example.com`）、モデル、入力・出力・キャッシュのトークン（報告がなければ空）、最初の文字までの時間（文字のない答え、つまり道具の呼び出しだけなら空）、全体の時間、結果（`completed`・`failed`・読み切らなかった `stopped`）。
- 集計（`stats/models`、引数 `days` 既定 30・`utc_offset_minutes` 既定 0）：提供元とモデルごとに、件数、失敗の数、トークンの合計、キャッシュの割合（キャッシュ ÷ 入力）、完了した要求の最初の文字までの時間の中央値、速さの中央値。速さは出力のトークン ÷（全体の時間 − 最初の文字までの時間）、最初の文字の時刻がなければ全体の時間で割る。時間帯（呼んだ側の時差で数えた 0〜23 時）ごとにも同じ値を返す。件数の多い順。

## 検証

- 単体テスト（`core/src/usage_log.rs`）：記録と集計（件数、失敗、トークン、キャッシュの割合、中央値、時間帯、時差、期間の絞り込み）、日をまたぐ時間帯。
- 結合テスト `near_the_window_older_work_is_compacted_and_the_person_kept` の最後：圧縮の要約も含め、模擬 API に届いた要求の数と記録の数が同じこと。
- 結合テスト `requests_are_logged_and_summed_up_per_model`：2 回のターンの後、`stats/models` にそのモデルの 2 件が出ること、範囲外の時差を断ること。
- 未検証：実際の提供元での最初の文字までの時間（提供元によっては最初の区切りが早く届く）、DeepAI の記録。
