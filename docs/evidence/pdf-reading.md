# PDF を読む

- **きっかけ：** 2026-11-23 ユーザー「あとpdfよむとかそういったのはできるの？」「pdfもgitも効率的な方法調べて」。

## 資料（論文の結果）

- **OmniDocBench**, CVPR 2025（査読あり）, arXiv 2412.07626。
  - 9 種類の文書で比べた。普通の論文や報告書では、組み立て式の変換（MinerU・Mathpix）が文字・数式・表で最もよかった。
  - 傷んだスキャンや変わった配置では、画像を読むモデルのほうがよかった。
  - 測っているのは変換の正確さで、LLM の答えやトークンの量は測っていない。
- **olmOCR**, arXiv 2502.18443（査読前。ACL 2026 のデモ版あり）。1,402 個の PDF で 7,010 項目を合否判定した。
  - 成績：olmOCR 75.5、Mistral OCR 72.0、Marker 70.1、GPT-4o 69.9、MinerU 61.5。
  - ページ画像に、その PDF から取り出した文字と位置を添えた。Gemini Flash 2 は 57.8 → 63.8 に上がった。GPT-4o は +1.0 で、誤差の範囲。
- **MMLongBench-Doc**, NeurIPS 2024 Datasets and Benchmarks（査読あり）, arXiv 2407.01523。長い文書に対する問答。
  - 画像を読むモデル 14 個のうち 12 個は、ページの画像を渡すより、OCR の文字を渡した同等の文字モデルに負けた。例外は GPT-4o と GPT-4V。
  - 最高でも F1 42.7%。
- **Adhikari & Agarwal**, arXiv 2410.09871（査読前）。DocLayNet で 10 個の解析器を比べた。
  - 文字と語順は、たいていの分類で PyMuPDF と pypdfium2 が最もよかった。論文や特許では、学習型（Nougat）が勝った。
  - 規則だけで表を取り出す方法は、多くの表を取りこぼした。

## 公式の仕様

- **Anthropic**（https://platform.claude.com/docs/en/build-with-claude/pdf-support）
  - `document` ブロックで渡すと、ページごとに文字とページ画像の両方がモデルに入る。
  - 費用はページあたり、文字が約 1,500〜3,000 トークン、画像が最大 1,568 トークン。
  - 上限：1 回の要求で 600 ページ（文脈が 1M 未満なら 100）、128 MB。
- **OpenAI**（https://developers.openai.com/api/docs/guides/pdf-files）
  - Responses API の `input_file` で渡すと、文字とページ画像を取り出してモデルに渡す。トークンが増えると明記している。
  - 上限：1 ファイル 50 MB、1 回の要求で 50 MB。
- **その他の OpenAI 互換 API**：PDF を受け取る保証は無い。OpenRouter は、読めないモデルには先に文字へ変換する（有料の OCR か、無料の変換）。DeepAI は確認していない。

## ほかの道具の作り（下調べの係が文書とソースで確認）

| 道具 | やり方 |
|---|---|
| Claude Code | 短い PDF はそのまま渡す。10 ページを超えるとページの範囲指定が要り、1 回 20 ページまで。範囲指定のときは poppler の `pdftoppm` でページを画像にする（入っていないと失敗する）。 |
| Gemini CLI | ファイル全体を base64 で渡す。文字の取り出しもページの範囲指定も無い。 |
| opencode | PDF を読めるモデルには添付として渡す。読めないモデルには短い断り書きを渡す。20 MiB まで。 |
| Cline・Codex CLI・Aider | 未確認。 |

確かめた道具の中に、自分で文字を取り出すものは無かった。

## Rust の部品（ライセンスは記憶によるものが多く、未確認）

- `pdf-extract`（`lopdf` の上に作られている）：文字だけを取り出す。Rust だけで書かれている。込み入った配置での品質は測られていない。
- `pdfium-render`：文字の取り出しとページの画像化ができ、品質が高い（Chrome の PDFium を使う）。ただし PDFium のライブラリが別に要る。
- `hayro`：Rust だけでページを画像にする。MIT／Apache-2.0。時間切れやメモリ不足の注意書きがあり、API はまだ変わる。
- `mupdf`：AGPL-3.0 で、このプロジェクトには合わない。

## 効率のよい作りの候補（推測。試していない）

1. **ページの範囲を指定して、ページごとに文字を取り出す。**
   - 普通の電子 PDF では、文字の取り出しの品質が高いことの支えがある（Adhikari & Agarwal）。
   - そのまま渡すとページあたり 1,500〜3,000 トークンに画像分が加わる（Anthropic）。文字だけならそれより少ないと見込むが、測っていない。
2. **文字がほとんど無いページ（スキャン）や、図・表を求められたときだけ、ページの画像を渡す。**
   - 支え：文字だけの取り出しは、スキャン・表・数式で失敗する（OmniDocBench・olmOCR）。
   - 「文字が少ない」の線引きには根拠が無い。
3. **画像を渡すときは、そのページの文字も添える。** 支え：olmOCR（Gemini Flash 2 では効いた。GPT-4o では誤差の範囲）。
4. **PDF をそのまま受け取る提供元（Anthropic・OpenAI）には、範囲が小さいときにそのまま渡す選択肢もある。** ページあたりの費用は高い。
